# Tasks

A task has one of five statuses: Backlog, Todo, In progress, Done and Closed. Four of them have a fixed color; Backlog has none. Tasks work as a to-do list: in a place's own view every task row starts with a round completion control that marks it Done in one click, a task can be added by typing its title, and any status can be set from any other. On top of that, a task keeps what Raft adds to a to-do: an assignee who can be a person or an agent, and its own discussion. In review is retired ([decision 0043](../decisions/0043-in-review-retired.md)): a task from before task conversations can still be in it, and keeps its chip and its group or column until it moves. Tasks are shown in two kinds of view. A place's own view (its Tasks section beside its conversation, the list under a message) shows compact rows and opens a task's details in a centered dialog. A product's page of tasks from several places shows a list or a board under one toolbar, lists the person's own work first, lets people act on many tasks at once, and opens a task in a column beside the list ([A page of tasks](#a-page-of-tasks); [decision 0045](../decisions/0045-the-tasks-page.md)). People and agents work from the same task, so a task's row, chip and details look and behave the same on every screen that shows it.

## When it applies

A product's page of tasks and the task view of a place. In Raft Chat these are the Tasks destination and a channel's Tasks section ([Raft Chat — Tasks](../products/raft-chat/tasks.md)); which filters and which create actions a product offers is on its own page. Where the two kinds of view differ, each rule below says which one it is for.

## Structure

```example
tasks/compositions/tasks-panel
```

Not yet implemented in raft-ui: this example shows the tasks before [0042](../decisions/0042-tasks-as-a-to-do-list.md), with five statuses, no completion control and no quick add. The rules on this page describe the redesign.

- **A page of tasks** (a product's page of tasks from several places): a head with the title and the count, a toolbar under it (Mine / All, the search, the filters, the sort, List / Board and New task), then the list or the board ([A page of tasks](#a-page-of-tasks)). On a phone, List / Board shows only its icons ([SegmentedControl](../../packages/ui/src/components/segmented-control/segmented-control.md)).
  - The list is grouped by the person's relation to the task in Mine and is one flat list in All, never grouped by status. Its rows are selectable rows ([The list](#the-list)).
  - A board has one column per status, each 232px wide, in the order Backlog, Todo, In progress, Done, Closed, the way work flows from left to right, each with a collapsible heading and a count ([TaskBoard](../../packages/ui/src/components/task-board/task-board.md)). Its cards are [TaskCards](../../packages/ui/src/components/task-card/task-card.md).
- **A place's Tasks section**: compact rows grouped by status, beside the place's conversation ([Tasks beside a conversation](#tasks-beside-a-conversation)).
- **Task details**: opened from a place's view, a centered dialog, 960px wide (or the window less 32px) and at most 900px high (86% of the window), full screen on a phone. Opened from a page of tasks, the same parts stand in a column of the page's row instead, beside the list ([The open task](#the-open-task)). From top to bottom:
  1. A bar with the task's reference (`#design:#25`: the place, then the number; see [Referring to a task](#referring-to-a-task)), in a product with conversations the agents that follow the task and the More menu (Follow task or Unfollow task, then a separator and Delete task), as in a thread's header ([Threads](./conversation.md#threads)), and ×. In a column of a page's row, Expand comes between the More menu and ×, as in a thread's head ([Panel](../../packages/ui/src/components/panel/panel.md#rules)). On a phone the bar has Back instead of ×. The bar has no button to open the task in a window of its own, as a thread has none: a task window opens from its URL, the same way a thread window does.
  2. The title and the description, which folds after 3 lines. Both are edited in place ([Editing a task](#editing-a-task)).
  3. The properties in an inline [DescriptionList](../../packages/ui/src/components/description-list/description-list.md#inline) (`direction="inline"`): Status, Assignee, Source, Created by and Created at. The assignee reads as on a task row, avatar and name. Source is there only for a task created from a message: the sender's avatar and name, the first line of the message and its time. On a line of properties, the texts share one baseline: the labels, the status chip's and the assignee's names, Source's sender and excerpt, and the times ([Text of different sizes on one line](../foundations/alignment.md#text-of-different-sizes-on-one-line)). The marks without text, the avatars, the chevrons and the ↗ after Source, are centered on the row's line box ([A mark that leads text](../foundations/alignment.md#a-mark-that-leads-text)). No trimming of the text and no nudges. A task row follows the same rule ([Rows in a compact list](#rows-in-a-compact-list)). A task created before tasks had their own discussion also gets Earlier discussion, with the number of replies its message has.
     Every property follows the one flow of an inline DescriptionList: the facts run on like a line of text, 24px apart, and a fact moves to the next line, 8px under, only when it doesn't fit on this one. No fact gets a line, a width or a gap of its own. Every fact is the same 28px row, so the lines are evenly spaced, their centers 36px apart: the line with the status chip and the assignee's avatar is no taller than a line of plain text, and the avatar's presence light shows whole, never cut by its trigger. Each fact is at most 24rem wide (or the dialog's width, if narrower), so a long Source ends in an ellipsis and shares its line: in a desktop dialog Status, Assignee, Source and Created by stand on one line; on a phone, where each fact fills more of the line, they wrap in the same order with the same gaps. This flow, not a label/value grid, because the properties are a handful of short facts: a grid gives each its own line and pushes the discussion down.
  4. History, collapsed ([Timeline](../../packages/ui/src/components/timeline/timeline.md)).
  5. In a product with conversations, the task's discussion and its composer ("Message this task").

## Rules

- Use only the five statuses. "Needs you" is not a status: it is an action (the button of an action card) and an attention dot. Don't add a "needs you" group or color either: a sixth bucket would hold tasks that are also in one of the five, and what waits for a person already has its place in the conversation.
- Put work that someone created or parked and doesn't plan to do now in Backlog ("not now"), and work that won't be done in Closed. Backlog keeps a task that may come back without counting it as active work; Closed ends it. Backlog has no hue ([Color](../foundations/color.md#statuses)).
- On a page of tasks, default to the list, on a phone and on desktop alike, and remember the person's last choice. The list answers what the page is opened for: what waits on the person and how the work they handed out is going. A board answers which status each task is in, and with task conversations the status says less than who has the task and whether it moved (Noel's reading of what the page is for, taken up by stdrc with the hi-fi design, 2026-11-10, #wg-task-v2:8a7ae237). The board was the desktop default before, for its room for five columns; it is one press away.
- On a page's board, collapse only Closed by default: Closed is work that won't be done. Backlog, Todo, In progress and Done stay open, because on this page people check what landed as well as what moves, and each column reads its tasks a page at a time in the page's sort, so a long Done column costs nothing until it is scrolled (the rule: the approved hi-fi design, 2026-11-10; the reason: Jasper's reading, confirmed by Noel in #wg-task-v2:8a7ae237). In a place's Tasks section, Backlog, Done and Closed start collapsed: Backlog is work not planned now, Done and Closed only grow, and in a narrow section beside a conversation the work in progress is what people come for ([Tasks beside a conversation](#tasks-beside-a-conversation)). The page's list has no status groups: Mine leaves finished tasks out instead ([The list](#the-list)).
- Start every task row in a place's view (the Tasks section, the list under a message) with the completion control ([Completing a task](#completing-a-task)). On a page of tasks, rows and cards have no completion control: a row starts with its selection box, and a status is changed on the board, in the selection toolbar or in the task (stdrc, 2026-11-09, #wg-task-v2:8a7ae237: "why is there still a checkbox before the task"). A round control beside the square selection box would put two boxes at the start of a row that look alike and do different things; [0042](../decisions/0042-tasks-as-a-to-do-list.md) chose the circle because a square box there reads as "select this row", which on the page is what it is. On a card the status chip is the only thing that changes in place; selecting the rest of the card opens the task.
- Let people change status from the status chip on a card, from the Status property in the details, by dragging a card to another column of the board, with the completion control in a place's view, and on a page of tasks with Status in the selection toolbar, for every selected task at once. A person who can't change a task sees its chip without a menu and its completion control disabled, and can't drag its card; a change to several tasks skips the ones they can't change and says how many it skipped.
- Offer every status from every status, to people and agents alike: the chip's menu and the Status property list all five with a check on the current one, and a card can be dropped in any column of the board. There are no transition limits: a status says where the work is, and whoever knows that sets it in one step, while the event line and History keep who moved it and when. No status needs anything else first: an unassigned task can be In progress.
- Open task details from a place's view as a centered dialog, never in the side panel or a side section: a task holds its own discussion, so it isn't read beside the conversation ([Page structure](./page-structure.md#sidebar-and-side-panel)). Close it with ×, Esc or a press outside the dialog. On a page of tasks the task opens in a column of the page's row instead, the list standing as the row's conversation ([The open task](#the-open-task)): the page has no conversation of its own, so the task's discussion is the only one on screen, and the list stays in view for the next task (stdrc, 2026-11-09 and 2026-11-10, #wg-task-v2:8a7ae237).
- Name the task's place on a card or a row only where tasks from several places are listed. In the view of one place, the place is already the page.
- While tasks load, show skeletons in the shape of what is coming: a skeleton card per column on a board, skeleton rows under the section headings in a list ([Feedback](./feedback.md#empty-loading-and-failed); [The first frame is the settled one](./responsive.md#the-first-frame-is-the-settled-one)).

### Moving a task to Backlog

- Ask for a reason when a task is moved into Backlog from another status, by any route: what would bring it back. Ask in a small [Popover](../../packages/ui/src/components/popover/popover.md) anchored to what the person used, the status chip, the Status property or the column the card was dropped on, with one single-line [Input](../../packages/ui/src/components/input/input.md), then Cancel and Move to Backlog. The reason is optional: Move to Backlog with the field empty moves the task without one.
- Cancel, Esc or a press outside the popover keeps the task where it was; a dropped card goes back to its column.
- Record a reason in the task's History and in the event line the move writes in its discussion: "Martin moved #25 to Backlog: waits for the server-side record". Without a reason the line is "Martin moved #25 to Backlog".
- Don't ask when a task is created in Backlog: a new task has nothing to come back from.

### Keyboard in a list of tasks

A list of tasks (the rows beside a conversation and under a message, the rows of a page of tasks, the cards of a [TaskList](../../packages/ui/src/components/task-list/task-list.md)) is a grid, so a long list costs one Tab and the arrow keys do the rest.

- Make the list `role="grid"` and each task a `role="row"`. Its cells are the completion control (on a page of tasks, the selection box) and the title cell, which opens the task; on a card the status chip is a third cell.
- Give the list one Tab stop, with a roving `tabindex`: Tab enters the list on the cell that last had focus (the first row's title cell at first), and the next Tab leaves it.
- Let ↑ and ↓ move to the same cell of the previous and next row, and ← and → move between the cells of a row.
- On the completion control, Space completes the task or reopens it. On the selection box, Space selects the row or clears it. On the title cell, Enter or Space opens the task.
- Show the focus ring on the focused cell ([Focus](../foundations/states.md#focus)). When a completed task leaves for the collapsed Done group, move focus to the same cell of the next row, so the keyboard stays in the list.
- On the board, Space on a card still picks it up to move it ([TaskBoard](../../packages/ui/src/components/task-board/task-board.md#accessibility)).

### Completing a task

The completion control is how a to-do list is worked through: one click and the task is done. It leads every task row and card, beside a conversation, under a message, on the board and in the list.

- Use [TaskCompletionControl](../../packages/ui/src/components/task-completion-control/task-completion-control.md): a round `CheckboxIndicator` (`shape="circle"`) inside a `button` with `role="checkbox"`, `aria-checked` true only on a done task. It is round, not the square of a [Checkbox](../../packages/ui/src/components/checkbox/checkbox.md), for the reason in [Shape](../foundations/shape.md#principles).
- Name it by the task, and keep the name when the state changes: "#25 Fix onboarding copy". The checked state already says whether it is done, so a name that says what a click does ("Reopen #25") would be read as "Reopen #25, checkbox, checked". Its tooltip may say the action: Complete, Reopen on a done one.
- Show it checked only on a done task. On every other status, Backlog and Closed included, it is unchecked, and a click marks the task Done, as any change of status does.
- While unchecked, preview the check when the pointer is over the control itself (`previewOnHover`), never over the rest of the row: hovering elsewhere on the row is a hover on the row, not on the control ([Hover and press](../foundations/states.md#hover-and-press)). TaskCompletionControl does this even when the row or a board column around it is a Tailwind `group`.
- Let one click mark the task Done from any status.
- Show the result in place, then move the task: the title is struck through in `foreground-hint`, a Toast says "Completed #25" with Undo ([Toast](../../packages/ui/src/components/toast/toast.md)), and the task stays in its group, struck through, for 650ms before it moves into the collapsed Done group; with reduced motion it moves at once ([Motion](../foundations/motion.md#usage)). Undo puts it back in the status it came from. A task that jumps away at the click reads as lost; the pause and the Toast say where it went.
- Let a click on a done task's control reopen it to Todo.
- Make the control its own button on top of the row or card. Its hit area reaches 8px past its 20px circle with a mouse (36px) and 12px on a touch screen (44px) ([Hit targets](../foundations/accessibility.md#hit-targets)). With a mouse it reaches 8px, not 12px, so it never covers the task's number beside it. Selecting the rest of the row or card still opens the task.
- For a person who can't change the task, show the control disabled with `aria-disabled` only, never the native `disabled`: the button keeps keyboard focus, so moving through the grid still stops on it, a screen reader says it is unavailable and its tooltip can explain why. Pressing it or Space does nothing. Style it from `data-disabled`. TaskCompletionControl's `disabled` does all of this.

### Where tasks are created

- Every task belongs to one place, so every way of creating one says which. In a place, the place is the one the person is in. On a product's page of tasks from several places, the page has a New task button at the end of its toolbar, and the Create task it opens asks for the place (below); the page has no quick add, because one keystroke can't say which place. The page keeps New task because it is where people go to manage tasks, and the earlier Tasks page already had it: the redesign was to lose none of what that page could do (stdrc, 2026-11-10, #wg-task-v2:8a7ae237).
- In a place with a conversation, put a create button in the head of its Tasks section ([Tasks beside a conversation](#tasks-beside-a-conversation)), the quick add under its All / For me, and Create task from message in the message menu.
- Make the quick add an input row with the placeholder "Add a task". Enter creates a Todo task with that title; in For me it is assigned to the person, in All it is unassigned. Focus stays in the input, empty, for the next task. Esc clears the input, and in an empty input it moves focus out of it. It creates a task in one keystroke, as a to-do list does; anything more (a description, another status, an assignee) is in Create task or in the task's details afterwards.
- Make Create task a small form dialog ([Forms](./forms.md#forms-in-a-dialog)), from top to bottom:
  1. On a page of tasks only, Channel (the place): a picker with search over the places the person can create a task in, A to Z, filled in when the page's place filter has exactly one value and otherwise empty. It is required, and an empty one is reported on the field when the form is submitted ("Pick a channel"). The task opens beside the list once it is created.
  2. The titles: one input per task, and Add another to create several at once. With more than one title the dialog is Create tasks and its button says how many ("Create 3 tasks").
  3. Description, optional, only while there is exactly one title: a description belongs to one task.
  4. Status and Assignee, side by side. Status offers Backlog, Todo and In progress, Todo by default, each with its pixel. Assignee lists Unassigned, then the people and the agents who can take the task, Unassigned by default; any status can go with any assignee, Unassigned included. Done and Closed can't be chosen: a task gets there through its work, not at its creation. The status and the assignee apply to every title.
  5. With more than one title, a line under them: "Status and assignee apply to all 3 tasks."
- Check the form when it is submitted, as every form does ([Validation](./forms.md#validation)): nothing disables the create button while the form is filled in.
- Not yet implemented in raft-ui: the Create task example (`tasks/compositions/create-task-dialog`) shows the dialog before this redesign, with titles only.

### Editing a task

- Edit the title and the description in place in the task details: select the text, or its Edit button (a ghost `pencil` icon button that shows on hover and on focus), to turn it into a field. Enter or leaving the field saves; Esc cancels and restores the text. In the description Shift+Enter starts a new line. A task without a description shows "Add a description" in its place.
- Write a saved change as an event line in the task's discussion ("Martin changed the title", "Martin changed the description"). A change of wording notifies nobody else: followers see the line when they next read the task.
- Put Delete task last in the details' More menu, after a separator. It asks first, as every deletion does ([Confirming](./feedback.md#confirming)).

### Tasks in a conversation

In a product where tasks come from conversations, a task is created from a message; the message is not the task. The task has its own title, description and discussion, and links back to the message it came from. A message can be the source of several tasks, and a task can belong to the place without any message.

- Show the tasks created from a message as a list under its content and above its replies: one row per task with the completion control, the number (`#25`), the title followed by the number of messages in its discussion, then the assignee (avatar and name; the person reads "You") and the status chip together at the right. A list holds any number of tasks; the replies stay the discussion of the message itself. The rows are the compact rows of [Rows in a compact list](#rows-in-a-compact-list).
- Size the box that holds the list by its content: at least 320px wide (or the whole column, if that is narrower) and at most the width of the message column. Keep a title to one line and end it with an ellipsis when the row runs out of room: a task created before tasks had their own discussion has the whole message as its title, and its details show all of it.
- Put the number of messages right after the title, inline: right after its last word, or right after the ellipsis when the title is cut, with the same small space either way. Never leave a gap between a cut title and the number: the title gives up only the room the row lacks. It counts the discussion the title names, so it belongs to the title, not to the assignee.
- Keep the assignee and the status chip as one group at the right of each row, the assignee right next to the chip. Don't line them up in columns across rows. Where a row is too narrow for a readable title and the group, the group wraps, as a whole, to a second line, still at the right, instead of squeezing the title.
- Show the same list under the message at the top of its thread.
- Open the task details from a row. The completion control is the one thing on the row that changes the task: selecting the rest of the row opens the task, and every other change of status is made in the details.
- Let people create tasks from a message with Create task from message in the message menu. It opens Create task with the message quoted and its text as the first title, which they can change.
- Don't offer As task in the composer: people send messages, and tasks are created from them afterwards, by a person or an agent.
- Write what happens to a task as event lines in the task's discussion: created, claimed, assigned, moved, completed ("Martin completed #25"), reopened, moved to Backlog with its reason, and its title or description changed. Not in the conversation and not in the thread of the message it came from ([Hand-offs and approvals](../people-and-agents/handoffs-and-approvals.md#claiming-work)).
- Show the task's discussion inside the task details, so the discussion and the status are read together. Follow a task as you follow a thread ([Hand-offs and approvals](../people-and-agents/handoffs-and-approvals.md#following-a-task)).
- In the details of a task created from a message, select Source to close the dialog and jump to the message in its place, which shows the located highlight, as every jump does ([Located](../foundations/states.md#located)). Select earlier discussion to open the replies of the message the task used to be.
- Show the number of messages in a task's discussion, in Space Mono, once it has any. Add the attention dot before it only for people who follow the task.
- A task created before tasks had their own discussion, when the message was the task, gets one only when something is first written to it. Show an empty state in its place ("No discussion in this task yet", saying the earlier discussion is in the replies of its message) with the composer ready, not the message's replies; the first message starts the task's discussion.

### Pulling the task head down

On a phone, and on the web wherever the task details are full screen, the task's head (the title, the description, the properties and History) is the conversation's first row and scrolls away with it. Scrolling back up to read the status would lose the reader's place in the discussion, so the bar pulls the head down over the conversation instead.

- Once the head has scrolled out of view, the bar collapses: under the reference line, `Task #N`, the status chip and the assignee's avatar alone, then a small chevron. The avatar is named for screen readers; the name shows beside it only where the bar has room for it whole. The reference line (`#design:#25`) stays in both states. Until the head has scrolled away, the line under it is `Task #N` alone, with no status chip, avatar, or chevron.
- A tap on the bar pulls the head down as a panel that hangs from under the bar across its whole width, over the conversation. It is the same head as the conversation's first row, editable the same way (Status, Assignee, Show more, Source, History). No scrim, and nothing under it moves.
- Draw the panel on `layer-canvas` with `shadow-float` along its edge and no 1px divider: the shadow already parts it from the conversation, and a hairline on top of a shadow is a second edge saying the same thing ([Elevation](../foundations/elevation.md#tokens)). It is at most 70% of the screen tall; beyond that its own content scrolls.
- It slides down from the bar and back up in 220ms with `ease-slide`, the shortest slide ([Motion](../foundations/motion.md#usage)), and the chevron turns with it. With reduced motion it appears and goes at once.
- It closes on:
  - a second tap on the bar;
  - a tap outside it, including the composer and its buttons. The tap still lands where it was aimed. A menu the head opened (Status, Assignee) is inside the panel;
  - focus moving outside it, such as into the composer;
  - Back, the system back on a phone, and Esc. Back closes the panel before it leaves the page;
  - an upward swipe of at least 40px on the panel once its content is scrolled to its end. Until then the swipe scrolls the panel's content;
  - the reader starting to scroll the conversation. An arriving message does not close it;
  - the head scrolling back into view.
- The panel doesn't follow the finger: a swipe up past 40px closes it with the same slide, and a shorter one leaves it where it is. A panel that tracks the finger looks like a sheet that can be dragged to any height, which this panel can't. This holds on the web and on a phone (decided 2026-10-28).
- Focus moves into the panel when it opens and back to the bar when it closes, except after a tap outside: that tap puts focus where the reader meant. The bar is a button with `aria-expanded` that controls the panel, named by what it shows ("Task #7, In progress, Kirby"); the panel is a region named by the task ("Task #7").
- Keep the conversation bottom-anchored, newest message on the composer, and let the head fold away only as far as the conversation fills the room it leaves. A short task keeps its head in view and shows no gap above "Beginning of conversation"; its bar never collapses, so there is nothing to pull down.
- On a tablet or a wide window the head stays pinned above the conversation, so there is no collapsed bar and no panel.

The web builds this as `TaskHeadPullDown` (slock `packages/web/src/components/task/TaskHeadPullDown.tsx`, slock #11722); the phone as `RaftPullDownPanel` (mobile #3884), with the fold limit that keeps a short task free of a gap in mobile #3899. It is not a [Popover](../../packages/ui/src/components/popover/popover.md) or a [Drawer](../../packages/ui/src/components/drawer/drawer.md): it is neither modal nor anchored to a point.

### Tasks beside a conversation

A place's tasks open as a Tasks section beside its conversation ([Page structure](./page-structure.md#sidebar-and-side-panel)), so people see the work moving while they talk. People don't need to read every task there: the section answers what is moving and what waits for them.

- Put the title Tasks in the section's head, then the create button, ⋯ (with Move left and Move right where the section can move), Expand and × ([Panel](../../packages/ui/src/components/panel/panel.md#rules)); where the head runs out of room, the create button folds into the ⋯ as New task. The header has no count: the All and For me filter right under it already carries the numbers. On a phone the section covers the conversation under the place's header, and the header's Back closes it: the section draws no Back or × of its own, so there is one Back on screen.
- Under the header, put All / For me ([SegmentedControl](../../packages/ui/src/components/segmented-control/segmented-control.md)), each with the number of its active tasks: Todo and In progress. Backlog, Done and Closed are not counted, since none of them is work going on now. For me lists the tasks assigned to the person.
- Right under All / For me, put the quick add, an input row with the placeholder "Add a task", on the section's margin, 20px on a touch screen and 16px with a mouse ([Where tasks are created](#where-tasks-are-created)). The head's create button still opens Create task, for a description, another status or several tasks at once.
- Group the tasks by status in the order In progress, Todo, Backlog, Done, Closed: in a narrow section the work that is moving comes first, then what waits, then what is over. Each group has a collapsible heading in gray with the status pixel and a count, and Backlog, Done and Closed start collapsed. Each heading has 16px above its words and 6px below, in a 40px box (the spacing the [Sidebar](../../packages/ui/src/components/sidebar/sidebar.md) section header had before its list took the 8px under it), and the groups have no gap of their own, so a heading sits on its own rows, noticeably farther from the group above (about 25px) than from its first row (16px) ([Spacing rhythm](../foundations/comfort.md#spacing-rhythm)). By touch its target reaches 4px up, to 44px.
- Give each task one compact row: the completion control, the number, the title on one line (ending in an ellipsis when cut) with the number of messages in its discussion right after it, then the assignee (avatar and name; an agent's avatar carries its presence light, and the person reads "You") and a chevron at the right. Leave the status chip out of the row: the group already names the status. Where the section is too narrow, the assignee wraps to a second line at the right, as in the list under a message. The rows are the same compact rows as under a message and in the Files section ([Rows in a compact list](#rows-in-a-compact-list)).
- Open the task details from a row, in the centered dialog ([Rules](#rules)). The section stands beside the place's conversation, so its task doesn't open as another column beside it, as a page of tasks' task does ([The open task](#the-open-task)).

### A page of tasks

A product's page of tasks collects the tasks of every place the person can see. People open it to answer two questions first, what waits on them and how the work they handed out is going, and then to find any task, act on many at once and read one. The rules here are for that page; where a place's Tasks section differs, the section keeps its own rules ([Tasks beside a conversation](#tasks-beside-a-conversation)). What Raft Chat calls its parts is in [Raft Chat — Tasks](../products/raft-chat/tasks.md).

- Give the page the whole width right of the rail, with no sidebar and no column of fixed width in the middle: the list is the page's main content, as a conversation is a channel's, and a list held to a strip in the middle wastes the room a long title needs (stdrc, 2026-11-10, #wg-task-v2:8a7ae237).
- Put the title and the count in the head, the count in Space Mono beside the title. On a phone they are the tab's top bar. The search field is in the toolbar, not the head ([A page of a list](./page-structure.md#a-page-of-a-list)). The count is the number of tasks in the current tab, the ones its list shows: in Mine the person's unfinished tasks and the tasks they started that were done in the last day, not every task of theirs; in All every task the person can see (Noel, 2026-11-10, #wg-task-v2:8a7ae237). While a filter or the search narrows the list, it is the number shown, a slash, then that total ("3 / 12"), so a narrowed list never reads as the whole one.
- Put the toolbar under the head: Mine / All with their numbers first, then the search field, filling the line, then the filters and Clear all while a filter is applied, then at its end the sort, List / Board and New task, the one primary button. The search moved here from the head: it decides what the list shows together with the filters, and in the head it was the first thing squeezed out when the page narrowed (stdrc asked Jasper to decide from research, #proj-raft-ui:f9756e85, 2026-11-10). It is one Tab stop ([FitToolbar](../../packages/ui/src/components/fit-toolbar/fit-toolbar.md)), takes at most two lines, and once the filters have a line of their own, that line scrolls sideways ([The toolbar over a list](./responsive.md#the-toolbar-over-a-list)).

#### Mine and All

- Offer two tabs, Mine and All, in a [SegmentedControl](../../packages/ui/src/components/segmented-control/segmented-control.md), each with its number of tasks. Mine holds the person's own tasks: assigned to them, created by them, or created from a message of theirs. All holds every task the person can see. Two tabs, because the page has two jobs: Mine is what anyone who opens it wants first, All is for finding and looking after the rest (stdrc, 2026-11-10, #wg-task-v2:8a7ae237).
- Open Mine the first time, and after that the tab the person chose last, kept for each person in each server.
- Let every filter and the sort work in both tabs. All with Assignee set to Unassigned is the list of tasks nobody has, and All sorted by least recently updated is the list of tasks nobody has moved: earlier designs gave each a section of its own, and the filters give them without adding one (stdrc, 2026-11-10).

#### The list

- In Mine, show two sections, in this order: the tasks assigned to the person, then the tasks they started (created, or created from their message) that are someone else's or nobody's. A task is in one section only, the first it fits. Without a status filter, leave finished tasks out: the first section lists Backlog, Todo and In progress, and the second adds the tasks done in the last day, so the person sees the work they handed out land. With a status filter, each section lists the statuses chosen.
- In All, show one flat list.
- Don't group the list by status: the status is on every row, and who has a task and whether it moved say more about it than which status it is in (Noel's reading of what the page is for, taken up by stdrc with the hi-fi design, 2026-11-10).
- Give each section a heading with its count, in Space Mono, and no line of explanation under it: a sentence under a heading is one more thing to read on every visit (stdrc, 2026-11-10, #wg-task-v2:8a7ae237: too much explanatory text). A section with no task keeps its heading and says so in one line, without naming the section again: the heading already does (Noel, 2026-11-10, #wg-task-v2:8a7ae237).
- Order the rows by the page's sort, most recently updated first by default: Recently updated, Least recently updated or Recently created. An update is the task's last activity, a message in its discussion included.
- Read the rows 20 at a time and the next 20 as the list scrolls. The counts in the head, the tabs and the headings are the totals, never the number loaded.
- Never let the list scroll sideways (stdrc, 2026-11-10, #wg-task-v2:8a7ae237: a title that is too long wraps; a sideways scroll makes no sense). The list scrolls up and down only. A long title wraps onto more lines, and a word longer than the line breaks anywhere, as text in a table does ([Table](../../packages/ui/src/components/table/table.md#behavior)). Where the row narrows, its parts give way by the list's own width, never the window's ([Switch on the region's width](./responsive.md#switch-on-the-regions-width)): the reference keeps only its number and its place moves to the row's end, the status shows its pixel only ([Lists](./lists.md#wide-and-narrow)), and the parts at the end wrap, as a group, onto a second line at the right. Only the board scrolls sideways.
- Put each section's rows, or All's, in one box, `layer-card` with a `line-hairline` border and `radius-container`, with hairlines between them, as the list under a message ([Rows in a compact list](#rows-in-a-compact-list)). From start to end a row holds the selection box, the reference (`#design:#25`, in Space Mono and `foreground-hint`; on a phone `#25`, with the place at the row's end), the title in `text-callout`, then at the end the assignee (avatar and name, "You" for the person), the status chip and the time since the task last moved, in Space Mono. The section of tasks assigned to the person leaves the assignee out: it would be them on every row.
- Show the time in `warning-strong` on a Todo or In progress task nothing has moved for 3 days, and add it to the row's accessible name in words ("no update for 3 days"). The color marks a task that may be stuck without adding words to the row; the accessible name keeps the meaning from resting on color alone ([Accessibility](../foundations/accessibility.md#principles)).
- Fill the whole row on hover and press, `overlay-subtle` and `overlay-medium`, the selection box included: the box stands inside the fill, in a 20px slot 12px from the row's start by touch and 8px with a mouse, and the reference starts 8px after it. A fill that stopped at the box would cut the row in two (stdrc, 2026-11-10, #wg-task-v2:8a7ae237: the whole row turns gray, and the checkbox sits on the gray), and a leading checkbox stands inside a row's shape in every list ([Lists](./lists.md#one-edge)).
- Let a click anywhere on the row but its box open the task; the box only selects. The open task's row shows `fill-cell-selected` and carries `aria-current`.

#### Selecting tasks

- With a mouse, show a row's selection box on hover and on keyboard focus; once a task is selected, show every row's box until the selection ends. By touch there is no hover: a long press (500ms, moving no more than 10px) selects the row and starts selecting, since the row has no press-and-hold menu ([Toolbar for selected items](../components/overview.md#toolbar-for-selected-items)).
- While selecting, a click or a tap on a row selects it or clears it instead of opening it. Shift-click selects the run from the row picked last; ⌘-click or Ctrl-click selects a row as its box does; ⌘A or Ctrl+A, from the list or from nowhere, selects every task under the current tab and filters, the rows not loaded yet included, and never the cards of a collapsed column; Esc ends the selection ([The open task](#the-open-task) has the order of the Esc presses).
- On the board, ⌘-click or Ctrl-click selects cards, and dragging a selected card moves every selected card.
- Act on the selection with the [SelectionToolbar](../../packages/ui/src/components/selection-toolbar/selection-toolbar.md) floating at the bottom of the page, the one messages use (stdrc, 2026-11-10, #wg-task-v2:8a7ae237): the count, a hint when some tasks will be skipped ("2 will be skipped"), then Status, Assignee (Unassigned first, then the people and agents: a list of the values the task can take, as in Create task, never an action such as "Clear assignee"), Nudge, then Follow and Delete as `secondary` actions, More and ×. Status and Assignee open their menus upward, and Delete asks first ([Confirming](./feedback.md#confirming)). A task the person can't change is skipped, not a reason to refuse the rest, and the result says how many were skipped.
- Not yet built: Nudge sends each assignee one reminder listing their selected tasks, as an agent's idle reminder lists its open work, and writes one line in each task's discussion, so an agent is woken once, not once per task (Noel's design for stdrc's request, 2026-11-10).

#### The open task

- Open a task from the list or the board in a column of the page's row, right of the list, the way a thread opens beside a conversation: the list stands as the row's conversation and the task as one of its columns, with the same rules for widths, clipping and Expand ([The channel's side columns](./responsive.md#the-channels-side-columns); stdrc, 2026-11-10, #wg-task-v2:8a7ae237: the page's main part is like chat's, and the task works like the thread).
- Open the task's column at 400px, as a thread's and a profile's (stdrc, 2026-11-10: its default width should be about the thread's). Let its seam drag it down to 160px, its content kept at 320px and clipped under it, and up until the list is down to 160px. The list's content keeps 360px, a conversation's, and clips under it, so the list always stays in view, at least as a strip ([Spacing](../foundations/spacing.md#layout-widths)). The task's column shares its width with the profile panel.
- Give both heads Expand while a task is open (with the list alone the row has one column, so neither shows it): the task's after its More menu and before ×, the list's at the end of its head. Expanded, a column fills the row and the other stays a 160px strip; Expand again, or Esc, puts both back to the pixel ([Panel](../../packages/ui/src/components/panel/panel.md#rules)).
- Close the task with × or Esc. Each Esc undoes one thing, the most recent layer first: an expanded row is restored, then a selection ends, then the task closes, one per press. Esc counts here only while no field, menu or dialog has it: those take it first (Noel, 2026-11-10, #wg-task-v2:8a7ae237). Focus goes back to the task's row when it was in the task or nowhere ([Moving focus](../foundations/accessibility.md#moving-focus)).
- Let a task opened from the list replace the one open.
- On a phone, push the task as a page over the list, with Back, and hide the tab bar under it ([Navigation](./navigation.md#going-back)).

#### The board

- Show one column per status, Closed collapsed ([Rules](#rules)). A column reads its cards 20 at a time and the next as it scrolls.
- Order a column's cards by the page's sort, so a column is one drop target: a card dragged over it marks the whole column, and no place opens between two cards, since the sort would move the card anyway ([Drag and drop](./drag-and-drop.md#where-it-will-land); stdrc, 2026-11-10, #wg-task-v2:8a7ae237). With the keyboard, Left and Right move a picked-up card between columns.
- Give a card its reference, its title, its status chip (a menu of the five statuses), its assignee and the time since it last moved, with no completion control ([TaskCard](../../packages/ui/src/components/task-card/task-card.md)).

### Rows in a compact list

The tasks under a message, the Tasks section and the Files section are one kind of list and use one row. It is content: hairlines between the rows, the whole row the target, and no card for each row. These compact rows keep their lines for now; the other lists of rows (Activity, search, the sidebar, phone lists of ListRow cells) have none and draw their states on an inset shape ([Lists](./lists.md)). A row reads as one line: what it is on the left, who has it and where it stands on the right. The rows of a page of tasks are these rows, with three differences: a selection box where the completion control is, a title that wraps instead of ending in an ellipsis, and the time at the end ([The list](#the-list)).

| Part | Spec |
| --- | --- |
| Row | One line, at least 34px tall with a mouse (the desktop row height) and 44px on a phone or a touch screen ([Spacing](../foundations/spacing.md#hit-targets)), 5.5px above and below its content with a mouse, 6px by touch. Its inline padding is the margin of the column it sits in: 20px in a side section on a touch screen, 16px with a mouse and on a phone, so a row starts on the section head's line, and 12px inside the box under a message |
| Alignment | The texts on the row's line share one baseline: the task's number, the title, the number of messages, the assignee's name, the words of the status chip, a file's size and time ([Text of different sizes on one line](../foundations/alignment.md#text-of-different-sizes-on-one-line)). The marks without text, the completion control, the avatar, the status pixel, the chevron and the icons (a file's type icon, the icon of the number of messages, the actions), are centered on the title's line box ([A mark that leads text](../foundations/alignment.md#a-mark-that-leads-text)). No trimming of the text and no nudges, as on a line of properties |
| Completion control | A task row only, first on the row, 10px before the number ([Completing a task](#completing-a-task)). A file row has none |
| Leading | Optional, on the title's line: a task's number (`#25`) in Space Mono and `foreground-hint`, 8px before the title, or a file's 20px type icon or thumbnail |
| Title | `text-callout` in `foreground`, on one line, ending in an ellipsis when cut. A done task's title is struck through, in `foreground-hint` |
| Inline meta | Right after the title, 6px from it, or right after the ellipsis: a task's number of messages (an icon and the number in Space Mono) or a file's size in Space Mono. It belongs to the title, so the title gives up only the room the row lacks |
| Trailing group | At the right, its parts 8px apart. A task: the assignee (a 19px avatar and the name in `text-caption`), then the status chip or, in the Tasks section, a chevron. A file: the time it was shared, compact and in Space Mono (today the clock, in the person's 12-hour or 24-hour choice; earlier this year the month and day, Oct 21; an earlier year the date, 2025-10-21; the full date and time in its tooltip), then its actions (Jump to message and Download, or a ⋮ menu below 560px), the last icon box on the row's margin with its hit area hanging outward, sideways and 4px above and below, so a file row is as tall as a task row ([Alignment](../foundations/alignment.md#the-ends-of-a-header)). The group wraps, whole, to a second line, still at the right, only where the title would get less than 160px: at a side column's default 360px, a task row and a file row each stay on one line |
| Dividers | `line-hairline` between rows, running as far as the list's container visibly goes ([Separators](../foundations/comfort.md#separators)). Under a message the box holds only the rows, so its lines run edge to edge and meet its border. In a side section, floating or beside the messages, and on a phone, the list is one part of a section that also holds a head, a filter and group headings, or of a page with no edge at all, so its lines are inset by the row's inline padding on both sides: they start where the row's content starts and end where it ends, 20px in from each edge (16px on a phone). The hover still fills the whole row. None above the first row of a list or of a status group |
| Container | Under a message the rows sit in a box sized by its content (see [Tasks in a conversation](#tasks-in-a-conversation)): `line-hairline` border, `radius-container` (it is a container, [Shape](../foundations/shape.md)), `layer-card`. In a side section the rows run edge to edge with no gap between them, and the section's head, filter and group headings share their margin, 20px on a touch screen (16px with a mouse and on a phone) |
| Group headings | A status heading in the Tasks section folds its group. It is a label over its rows, not a row, so it takes the states of a collapsible group heading: hover and press turn its words and chevron from `foreground-hint` to `foreground`, with no fill and no underline, and keyboard focus shows the inset ring ([Collapsible group headings](../foundations/states.md#collapsible-group-headings)). A fill would read as one more row, and would frame the words unevenly, since the heading keeps its words at the bottom of its box, on the rows they name |
| States | Hover lays the subtle overlay (`overlay-subtle`) over the whole row, press the medium one (`overlay-medium`), keyboard focus an inset ring ([Hover and press](../foundations/states.md#hover-and-press)). The completion control shows its own focus ring. A file's actions stay their own buttons on top of the row; Jump to message lands on the message with the located highlight ([Located](../foundations/states.md#located)) |

- Don't give the rows of these lists a card each or a gap between them. A card per row turns a narrow side column into a stack of controls, and the three lists stop reading as one.
- Don't put a second line of details (size, time, role) under the title: details go in the inline meta or the trailing group. A row has a second line only when its trailing group wraps.
- Don't line up the trailing groups in columns across rows.

### Referring to a task

A task number is unique only in its place, so a reference names the place first: `#design:#25`, and `dm:@ada:#25` in a direct conversation. It reads as "#25 of #design" and opens the task from anywhere.

- Write a task reference as the place, `:`, then the number with its `#`. Agents write and read the same reference.
- Render a reference as a link that opens the task details, in any place, for people who can see that place. For anyone else it stays plain text.
- Render the link as the task chip in the task's status colors (its status pixel and soft tint), the same chip the task list under a message uses, so a reference reads "which task, and where it stands". Do not split the reference into differently colored parts: it is one name, and the status already has the pixel and the tint. When the product has not loaded the task (another place's task), it reads the task by place and number; until then the reference is an outlined chip, a `line-hairline` border around `foreground-muted` words, with no tint and no pixel. Never show it as a gray chip, which reads as Closed. A Backlog task's chip is outlined too; how the two differ is in [Color](../foundations/color.md#statuses).
- `#25` on its own still refers to task 25 of the place being read.

### Filters

Which filters a product offers is on its own page. Every filter follows the same rules:

- Make each filter a [PickerTriggerButton](../../packages/ui/src/components/picker-trigger-button/picker-trigger-button.md) that opens a list, with search where it can hold many values (places, people); a list of the five statuses has none. Several values can be chosen.
- Show an active filter as `info-soft` with the number of values chosen, in Space Mono, so a filtered view never looks like the whole list.
- In a filter on people, list people and agents together. Put the shortcuts first ("Created by me", "Assigned to me", then "Unassigned"), as rows of the list rather than separate buttons, without an avatar; then people and agents from A to Z.
- Show Clear all, a ghost button, after the filters while any filter is active.
- On a page of tasks, put the sort at the toolbar's end, before List / Board: a [Select](../../packages/ui/src/components/select/select.md) of one value that fills `info-soft` while it differs from the default, as an applied filter does.
- When the filters don't fit beside the search, give them a line of their own that scrolls sideways (FitToolbar's `overflow="scroll"`), at every width, on a desktop too, the applied filters first and always in view. A row of filters that wraps pushes the list down, while one that scrolls keeps every filter one swipe away (stdrc, 2026-11-10; [The toolbar over a list](./responsive.md#the-toolbar-over-a-list)).
- Keep the filters in the address, so a filtered view can be shared and reloaded. On a page of tasks the tab, the sort, the view and the search go there too.
