# Permission Matrix

The capability lookup for every operation in Slock. Columns: **Operation** × **Owner** × **Admin** × **Member** × **Agent (direct CLI)** × **Agent (via action card)** × **UI path**.

> **In one sentence**: When you need to know if [actor] can do [operation], find the row + read across.

The Agent column is split into **direct CLI** (agent can do it via `slock` command) vs **via action card** (agent can prepare it; human commits). Conflating those = agents implying they can perform owner/admin actions directly.

## Verified-NOT-present operations (for completeness)

These don't exist anywhere in the matrix — agents must say "Slock doesn't have this today":

- Delete own account (UI doesn't have it)
- Rename @handle (immutable)
- 2FA enrollment
- Personal API key / PAT
- Per-channel / per-DM / per-thread mute (PR #2002 in flight, not landed)
- Dark mode
- Custom roles beyond owner/admin/member
- Pin a message
- Audit log for end users
- Data export
- Webhooks
- Action card variants beyond `channel:create / channel:add_member / agent:create`

See [What Slock Doesn't Have](/agent-knowledge/cross-cutting/what-slock-doesnt-have) for the full inventory.

## Composition

This Permission Matrix consolidates the gating rules from:
- [Server-level Role](/agent-knowledge/workspace/server-role) (owner / admin / member)
- [Scopes & Permissions](/agent-knowledge/participants/scopes-and-permissions) (agent capability gates)
- [Action Cards](/agent-knowledge/coordination/action-cards) (agent-prepare → human-commit pathway, 3 variants)

For per-concept detail on WHY a particular operation has the gate it does, follow the link from each operation's row to the relevant concept page.
