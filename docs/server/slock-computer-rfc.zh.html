0. 这份 RFC 要解决什么

这不是一份只讨论 credential 命名的 RFC。它要重新定义 Slock 本机运行层的边界：大的 Computer control plane、每个 server attachment 对应的 thin server session worker、以及真正代表 agent 行动的 Agent Runner。

目标态里只有两类非 human principal：Computer 和 Agent Runner。Server session worker 只是 Computer control plane 下的实现角色，不是独立 principal，也不是 ACL subject。

主体身份作用
Humanuser JWT人在 Web / API 里操作
Slock Computersk_computer_*（按 server attachment 发放）本机长期 control plane，管理安装、credential storage、多 server attachment、update、logs、diagnostics、runner supervision
Server Session Worker无独立 principal某个 server attachment 下的 thin worker，负责连接该 server、转发 control / lifecycle、启动和监管本 server 下的 runner
Agent Runnersk_agent_*一个 agent 的实际运行进程，负责 runtime、workspace、tool、message、task 等 agent 行为

之前的实现把这些边界混在一起：legacy daemon 既是机器连接，又替 agent 调 API，又启动 runtime，又管理 workspace。这个模型可以跑 demo，但不适合长期支持 managed runner、self-hosted runner、权限隔离、审计和一台 Computer 接入多个 Slock server。

v0.8 的目标是把模型切清楚：

  1. Computer 是本机 control plane，不是 agent。
  2. Server session worker 是 per-server attachment 的 thin worker，不是 principal。
  3. Runner 是 agent 的执行主体，不是 Computer 或 server session worker 的内部 helper。
  4. managed runner 和 self-hosted runner 使用同一套 Agent Runner credential 和同一套 agent API。
  5. server 是唯一 mint authority；Computer 只能请求 server 发 runner credential，不能本地 mint。
  6. workspace、tool、message、task、reaction、reminder、profile、channel、thread、action-card 等 agent 行为都走 Runner 身份。

1. 当前模型的问题

1.1 legacy daemon 现在承担了太多角色

@slock-ai/daemon 当前是一个长生命周期 machine worker。它用 sk_machine_* 连接 /daemon/connect，内部同时承担这些职责：

  • AgentProcessManager：启动和停止 runtime CLI 子进程。
  • runtime bridge：连接 Claude / Codex / Kimi 等 CLI。
  • MCP chat bridge：把 runtime 的工具调用转成 Slock 行为。
  • workspace 管理：准备 agent 工作目录。
  • system prompt builder：拼接 agent prompt。
  • active agent API 调用者：通过 /internal/agent/:id/* 以 machine 身份代 agent 行动。

这些职责放在一个进程里，会产生一个根本问题：机器身份和 agent 行为身份没有分开。server 审计看到的是 machine 在替 agent 做事，而不是 agent runner 自己在做事。

这不要求立刻删除旧 daemon package。兼容期里 @slock-ai/daemon 可以继续作为 legacy entrypoint 存在，但它在新模型里只是启动 single-server Computer session 的 compatibility launcher。新代码不应该继续把 daemon 当作 principal 或目标架构中心。

1.2 slock-computer 当前只是 launcher，还不是完整 control plane

@slock-ai/computer 现在更像一个 Play / demo / onboarding bridge：

  • 通过 device-code attach。
  • 创建或恢复 machines row，clientType=computor。
  • 写入 SLOCK_HOME/computers/computer-<serverMachineId>/state.json。
  • mint sk_machine_* connection key。
  • 启动 @slock-ai/daemon@play。

这条路径能把本机接进 server，但它还没有表达出 v0.8 需要的目标模型：Computer 是 runner 之外的本机 control plane，负责多 server attachment、credential storage、update、logs、diagnostics 和 runner supervision；真正的 agent 行为由 Agent Runner 持有 sk_agent_* 后完成。

1.3 External Agent 不能只是另一个 daemon 模式

External Agent 的核心要求不是“让外部机器也能跑 legacy daemon”。它要求：

  • self-hosted runner 不需要 human slock login。
  • self-hosted runner 使用 agent-scoped credential。
  • self-hosted runner 的 API 和 managed runner 完全一致。
  • server 审计能看到是哪个 agent runner 在行动。
  • 未来 managed 和 self-hosted 的差异只来自部署方式，不来自权限模型。

如果继续让 Computer 或 server session worker 用 machine/computer key 代 agent 调用，就无法满足这个要求。

2.1 三层架构

Human

Human 使用 user JWT 访问 /api/*。这是人类 UI 和普通用户 API 的身份，不参与 runner data plane。

Slock Computer / Computer control plane

Slock Computer 是本机长期 control plane。它是用户理解里的“一台 Slock Computer”，可以挂多个 Slock server attachment。

每个 server attachment 使用一份 server-scoped sk_computer_*。所以 sk_computer_* 不是 account-level 或物理机器级全局 identity，而是“这台 Computer attach 到这个 server 的一段身份”。

Computer 可以做：

  • attach / detach。
  • heartbeat。
  • 上报 host capacity。
  • 管理多 server attachment。
  • 管理本机 credential storage boundary。
  • 管理 update / logs / diagnostics。
  • 启动和监管 server session worker。
  • 接收 server 的 spawn / stop runner 请求。
  • 向 server 请求某个 agent runner 的 credential。
  • 监督本机 runner process 的生命周期。
  • 上报 runner started / exited。

Computer 不可以做：

  • 代表 agent 发送消息。
  • 代表 agent 读 channel / thread / task。
  • 代表 agent claim task / react / schedule reminder / update profile。
  • 管理 agent workspace data plane。
  • 持有 agent key 超过 handoff 所需的最短窗口。
  • 本地生成 sk_agent_*。

Computer 是 host，不是 agent。

Server Session Worker

Server session worker 是 Computer control plane 为某个 server attachment 启动或内嵌的 thin worker。它没有独立 principal，不 mint 自己的 key，也不成为 ACL subject。它使用该 attachment 的 Computer authority 做 control-plane 工作。

Server session worker 可以做：

  • 连接某个 Slock server。
  • 维护该 server attachment 的 heartbeat / reconnect。
  • 接收该 server 的 control message。
  • 转发 lifecycle / runner supervision signal。
  • 启动 / 停止该 server 下的 Agent Runner。

Server session worker 不可以做：

  • 代表 agent 调 /internal/agent-api/*。
  • 持有 sk_agent_* 超过 handoff 所需的最短窗口。
  • 作为 lifecycle event producer 或 credential actor 出现在产品事件模型里。

兼容期内，现有 @slock-ai/daemon 可以实现这个 role；但 RFC 和新代码里应把它称为 server session worker，而不是继续把 daemon 当作目标态架构名词。

Agent Runner

Agent Runner 是一个 agent 的实际执行进程。它使用 sk_agent_*。

Runner 拥有：

  • runtime CLI 子进程。
  • MCP chat bridge。
  • agent workspace。
  • tool execution boundary。
  • agent-facing system prompt。
  • /internal/agent-api/* 调用权。
  • runner websocket 或 runner event stream。

Runner 是 agent 行为的 data-plane principal。server 审计 agent 行动时，应该看到 runner credential，而不是 Computer credential。

2.2 managed runner 和 self-hosted runner 是同一种东西

managed runner 和 self-hosted runner 的区别只在 provisioning。这里的 self-hosted 表示 runner 由用户或第三方部署和管理，不表示 self-hosted Slock server：

类型谁启动credential 来源API
Managed RunnerSlock Computer 根据 server 指令启动Computer 向 server 请求，server mint sk_agent_*/internal/agent-api/*
Self-hosted Runner用户或第三方在外部环境启动bootstrap / exchange 得到 sk_agent_*/internal/agent-api/*

两者不应该有两套 agent API。self-hosted runner 不是“用户脚本 + 特权 token”，managed runner 也不是“daemon 代 agent 调用”。它们都是 Agent Runner。

2.3 server 请求 Runner，不请求 Computer 兜底

workspace 和 agent 行为属于 Runner。server 如果需要 workspace 能力，应该请求 Runner：

  • Runner 在线且支持能力：执行。
  • Runner 离线：返回 runner_unavailable。
  • Runner 在线但当前 active session 不支持能力：返回 unsupported_capability。
  • credential 本身没有被授权：返回 capability_not_authorized。

不能 fallback 到 Computer host。Computer host 没有 agent workspace authority。

2.4 legacy daemon entrypoint

为了不破坏现有安装、脚本、CI 和用户启动方式，旧 @slock-ai/daemon package / binary 可以保留一段时间。

兼容规则：

  • 旧 daemon entrypoint 只做 bootstrap：读取旧配置，创建或选择一个 server attachment，然后启动 Computer core 的 single-server session mode。
  • 新能力进入 Computer control plane / server session worker / Agent Runner core，不继续长在 legacy daemon abstraction 上。
  • 日志和 version 可以在兼容期继续显示 daemon 版本，但协议/RFC 不把 daemon 当 principal、producer 或目标架构层。
  • 等 slock/computer、multi-server attachment、desktop shell、自更新稳定后，再决定 daemon package 是 thin wrapper 还是 deprecate。

也就是说：外部入口可以兼容旧 daemon，用法不马上断；内部依赖方向必须是 computer -> server session worker -> agent runner。

4.1 managed runner flow

Managed flow:

  1. Human 或 server 决定某个 Computer 上需要启动 agent A。
  2. server 向该 Computer 的对应 server session worker 下发 spawn intent。
  3. Server session worker 使用该 attachment 的 Computer credential 调 /internal/computer/runners/:agentId/credentials 请求 runner credential。
  4. server 校验 Computer 是否有权在这个 server 上为 agent A 请求 runner credential。
  5. server mint sk_agent_*，绑定 agent A、server、capability max set、expiry、audit metadata。
  6. Computer / server session worker 启动 runner wrapper，只在 handoff 阶段把 credential 交给 wrapper。
  7. wrapper 启动 chat bridge / runtime，并 scrub runtime child env。
  8. Runner 通过 /internal/agent-api/* 行动。
  9. Runner 上报 started / exited，server session worker 只转发 supervision signal，不进入 agent data plane。

4.2 self-hosted runner flow

Self-hosted runner 的权限模型和代码路径要保留，但本 PR 不发布用户可见 CLI onboarding 命令；该入口不属于 #1836 release surface。

  1. clientMode=self-hosted-runner 仍表示外部 runner 直接持有 sk_agent_*，并使用同一套 /internal/agent-api/* surface。
  2. bootstrap token issue / exchange primitive 可以保留为代码能力，但默认不在生产挂载；必须显式设置 SLOCK_SELF_HOSTED_RUNNER_BOOTSTRAP_ENABLED=true 才能启用 POST /api/agents/:id/bootstrap-tokens 和 POST /api/agent/login。
  3. 测试可以显式打开该 flag 验证 primitive；产品化 CLI / UI onboarding 文案后续再发。

未来启用时，server 通过 POST /api/agent/login exchange bootstrap token，mint sk_agent_*；runner 本地保存 agent-scoped credential，并使用 /internal/agent-api/* 发送消息、claim task、react、读事件、管理 reminder 等。

Self-hosted runner 不应该走 human device auth，也不应该拿 user JWT。

4.3 lifecycle events

Credential lifecycle 事件沿用 v0.6 §13 Q4 的约定：

  • credential_issued
  • credential_revoked
  • credential_first_used reserved but not active

credential_last_used_at 是 audit metadata，不是 lifecycle event，也不应该出现在 Activity Log 里当作一条事件。

Lifecycle event producer / actor 只认 principal，不认实现进程：

  • credential_issued / credential_revoked 的 actor 是 Computer principal。
  • subject 是 Agent Runner principal。
  • server session worker 不是 producer，不是 actor，也不是 subject。
  • server session worker start / stop / heartbeat / supervision 属于 operational telemetry stream，不进入 lifecycle event schema。

4.4 upgrade contract

v8.3 narrow append。本节锁定 slock-computer upgrade（CLI / web button / tray item 任一触发）的契约面，反转 PR-E narrow-v1 "只升 supervisor 不升 daemon" 的窄定义 —— 实测发现窄定义会让新 supervisor 期待新 daemon 协议、找到旧 daemon 时进入 skew，agent delivery wave 静默 reject（参考 #proj-daemon task #44 KIMI_RS field regression）。v8.3 将 upgrade target 锁回 atomic bundle。

1. Atomic install — supervisor + bundled daemon：upgrade target 是 Computer service unit = @slock-ai/computer supervisor + bundled @slock-ai/daemon，两个包作为同一个原子事务安装。

  • 不允许 supervisor 已升级但 daemon 仍是旧版的 in-between 状态。
  • Pre-swap failure 不触碰 active layout（active Computer service version 仍 prior）；post-swap restart failure 留 active layout = new bundle 并标 Computer service unhealthy（无自动 reverse-swap，参见 §11 v8.3.3 hard non-goal）。
  • 实现走 pnpm deploy --legacy --config.node-linker=hoisted 同 packaging path（与 daemon APP / Computer App 同一 deploy 模式）。

v0 install 路径（v8.3.3 cleanup — Hao msg=aee2822d / Adspectum msg=78a5382f / Cody msg=1bd65c54 / Jianwei msg=3e4418bf / tygg msg=6f83c613 一致 lock）：v0 不支持 post-swap rollback。两概念拆分：

  • 保留 staging fail-cleanup（pre-swap 失败 = 不提交，不是 rollback）：stage / verify 阶段任何失败 → 不触碰 active layout（用户面 Computer service version 仍 prior，零 disruption）、emit error code（UPGRADE_NETWORK_FAILED / UPGRADE_INTEGRITY_FAILED / UPGRADE_DEPS_CHANGED 之一）。Staging artifact 保留在 upgrade-staging/<version>/ 供 operator 检查 forensic evidence；same-version retry fail-closed 直到 operator 手动 rm -rf 清理（与 PR #2080 paths.ts JSDoc 锁定 same-version retry semantics 一致）。
  • 不允许 post-swap rollback / reverse-swap：active layout swap 一旦发生 → upgrade 视为 committed forward-only。后续 restart / runner ready 失败 → emit unhealthy + actionable hint，不自动切回旧版本。用户面 Computer service version 已 new（已 committed），status 标 unhealthy 引导 user 跑 `restart` / 重跑 `upgrade` / 人工 inspect。

不允许 "先装 supervisor 再装 daemon 失败 npm uninstall" 非原子兜底（实质等同 PR-E narrow-v1 skew 风险换皮）。Install 路径由以下 3-step stage / atomic swap / restart 流程承载（all paths 由 paths.ts::* 函数派生，不允许 implementation 直接写 ~/.slock/computer/... 字面量）：

  1. Stage：两个包 unpack/deploy 到 ~/.slock/computer/upgrade-staging/<version>/（不动 active path）。Stage 失败 → emit error，active layout 未触碰，staging artifact 保留供 forensic 检查（与上文 pre-swap fail-cleanup 段一致；与 PR #2080 paths.ts JSDoc same-version retry fail-closed 一致）；same-version retry 直到 operator 手动 rm -rf 清理才解锁。
  2. Swap：staging binary swap 到 active 路径，使用 platform's same-volume atomic directory move primitive（POSIX rename(2) / Windows MoveFileEx 等价），持有 Computer upgrade lock 屏蔽并发 upgrade。Lock 屏蔽规则：swap 期间，任何 runner spawn / status version read 都不允许观察到半 swap / 缺失的 active layout；如果 active path 在任意时刻不可用 → emit UPGRADE_SWAP_FAILED（active layout 未触碰，用户面 version 仍 prior，零 disruption）。Swap 完成 = upgrade committed forward-only。
  3. Restart：swap 后 bounded sequential restart agent runner（见 (2)）。任一 runner 在 timeout 内未上报 running_idle → emit UPGRADE_RESTART_FAILED + Computer service 标 unhealthy；不 reverse-swap，不 kill 已切到新 layout 的 runner。用户面 Computer service version = new（已 committed），actionable hint 引导 user 跑 `slock-computer restart` 或人工 inspect / 重跑 `upgrade`。

Forensic evidence：staging dir 失败时保留供 operator 检查（不自动删，需手动 rm -rf，与 PR #2080 paths.ts JSDoc 锁定语义一致）；upgrade.log 记完整 outcome + errorCode。Pre-swap failure (UPGRADE_NETWORK_FAILED / _INTEGRITY_FAILED / _DEPS_CHANGED / _SWAP_FAILED) → 用户面 Computer service version 仍 prior；post-swap failure (UPGRADE_RESTART_FAILED) → 用户面 version 已 new but unhealthy。

同时继承 PR-E 已 merge 的 daemon-resolution invariant（Computer package root anchored daemon resolution，head fe992e4e 已锁）：实现不允许回退到 exports-based / require.resolve-based daemon 入口解析路径；daemon binary 必须从已 swap 的 active computer/ root 锚定，否则 staging 期间 supervisor 找到的是 prior daemon，atomicity 形同虚设。

2. Bounded sequential restart of agent runners（v8.3.3 rename — Cody msg=67e6c1ec + Hao msg=e30c87ae + Jianwei msg=78d26baf 三家锁；"rolling restart" 词隐含 substitutability / HA / zero-downtime guarantee（web pods 模型），但 daemon/runner 是 per-server/per-agent 不可替代，rolling 框架不成立 —— contract 意图是 blast-radius 控制 + 资源/诊断约束，不是 HA/availability guarantee）：atomic swap 完成后，现有 agent runner subprocess 不允许同时全部 kill。

  • Bounded sequential restart（per-server bounded concurrency，v0 默认 1-at-a-time）。
  • 每个 runner restart 必须等待 replacement 上报 ready 后才 kill 下一个。
  • 目标：blast-radius 控制 + 资源/诊断约束（避免多 agent 同时 strand 入 activityKind=starting 死循环 / 同时 starting 会污染 supervisor 日志、争抢启动资源；参考 task #44 / task #50 真实 incident）。不承诺 user-visible availability / zero-downtime / failover —— managed runners 没有互相替代关系。
  • "两个 runner 不能同时 starting" invariant 保留，但解释为 blast-radius / 资源约束，不是 availability guarantee（旧 "rolling" framing 隐含的 substitutability 在 per-server/per-agent 模型不成立）。

"ready" 语义锁定：supervisor 收到 replacement runner 的 running_idle lifecycle event（同 v8.3 lifecycle event schema），不是进程 spawn 成功，不是 runtime 首个任意 event。READY_WAIT_TIMEOUT_MS = 30000（v0 默认）。

Timeout / hang 处理 — fail-loud no rollback（v8.3.3 cleanup）：任一 runner 在 timeout 内未上报 running_idle → supervisor emit UPGRADE_RESTART_FAILED + Computer service 整体标 unhealthy。不 reverse-swap、不 kill 已 restart 跑在新 layout 的 runner、不 切回旧版本。active layout 已 committed forward-only 到新 bundle，user 面 Computer service version = new but status = unhealthy。actionable hint 引导 user 跑 `slock-computer restart` / 人工 inspect / 重跑 `upgrade`。Recovery 是 user 主动行为，不是 contract 自动事务保证。

In-flight turn / tool call — explicit non-goal：bounded sequential restart 会中断 runner 当前 turn / tool call；不承诺 live migration。中断的 agent 恢复机制是 Slock inbox replay + agent workspace MEMORY.md/notes，与 #proj-daemon PR #2068 runtime switch = session reset 模型同向（参考 §11 hard non-goals）。

6. Failure modes — closed-set error codes（v8.3.3 cleanup — 7-value SCREAMING_SNAKE_CASE，CLI-facing error token convention，与 v8.2 §10.13 既有 LEGACY_DAEMON_RUNNING / LEGACY_KEY_OUTSIDE_ADOPT / NON_INTERACTIVE_SETUP_REQUIRES_FLAGS 同 case）。v8.3.3 RFC bump 做了一次 delete + 2 add：删 UPGRADE_ATOMIC_ROLLBACK（post-swap rollback 不支持，参见 §11 hard non-goals）；加 UPGRADE_SWAP_FAILED + UPGRADE_RESTART_FAILED 拆分 pre-commit vs post-commit failure 语义（Adspectum msg=f22e7a60 lock）：

  • UPGRADE_DEPS_CHANGED — pnpm-lock divergence 检测到（用户本地 lockfile 与目标 lockfile 不一致），fail-closed。不允许 silent overwrite lockfile。
  • UPGRADE_NETWORK_FAILED — npm registry 不可达 / fetch failed (stage phase pre-commit)。active layout 未触碰，用户面 version 仍 prior。
  • UPGRADE_INTEGRITY_FAILED — 下载包的 hash 校验 mismatch (stage phase pre-commit)。active layout 未触碰，用户面 version 仍 prior。
  • UPGRADE_SWAP_FAILED — atomic swap 步骤失败（rename(2) / MoveFileEx error；pre-commit）。active layout 未触碰，用户面 version 仍 prior，零 disruption；actionable hint 引导 user 重试 upgrade。
  • UPGRADE_RESTART_FAILED — swap 已 commit 但 bounded sequential restart 阶段 runner 在 READY_WAIT_TIMEOUT_MS 内未上报 running_idle (post-commit)。active layout 已切到 new bundle，不 reverse-swap；用户面 version = new but unhealthy；actionable hint 引导 user 跑 slock-computer restart / 人工 inspect。
  • UPGRADE_NO_TARGET — 当前 channel 无更新版本。
  • UPGRADE_ALREADY_RUNNING — 并发 upgrade 尝试（lock 已被持有）。

Pre-commit vs post-commit boundary：UPGRADE_SWAP_FAILED 之前（含 SWAP_FAILED 自身）= pre-commit，active layout 未触碰，rollback 等价于不做（不是 rollback，是 fail-cleanup）；UPGRADE_RESTART_FAILED = post-commit，active layout 已 new but unhealthy，无自动 reverse-swap。

Closed-set discipline：additive-only；现有 value rename 与 delete 同等禁止；v8.3.3 已通过 RFC bump 路径完成 ATOMIC_ROLLBACK delete + SWAP_FAILED/RESTART_FAILED add；后续新 failure mode 同样必须走 RFC bump（同 o11y RFC §7 3-part 标准 enum 演进规则）。

边界 — 本节 7-value closed-set 限于 upgrade attempt outcomes。doc 在别处 emit 但不在此 7-value 内的 codes 分属各自独立 closed-set，分别遵守自己的 RFC-bump discipline，不并入本集：

  • Pre-condition rejection codes：UPGRADE_REQUIRES_ADOPTION（§4.4.9）、CHANNEL_INVALID（§4.4.5，v6 §11 既有 stable code，非 v8.3 新增）
  • Informational codes：LEGACY_DAEMON_INSTALL_DETECTED（§4.4.8）

5.8 Default Computer display name

v8.2 narrow append。slock-computer attach 时未传 --name 的默认 Computer display name 必须来自本机 hostname，而不是字面量 "slock-computer"。多台机器接入同一 server 时默认不撞名。

Derivation rules（single point at paths.ts::deriveDefaultComputerName(hostname)）:

  • 输入：os.hostname()。
  • 去尾缀（case-insensitive）：.local、.lan、.home、.fritz.box、.localdomain。
  • 替换：whitespace / 单引号 / 双引号 → -。例：August's MacBook → August-s-MacBook。
  • trim 末尾 -。
  • 结果为空 → fallback slock-computer-<short-hostname-hash>（hash 取 hostname 的 8 位 hex 派生），避免 default-name collision spike。

Override:

  • slock-computer attach --name <name> 显式覆盖；server 接受任何合法 display name。
  • server canonical 字段：computers.displayName。

Identity tuple + collision policy (matches computerCredentialService.ts::attachComputer; current staging code returns only ok | not_authorized, no displayName-collision path):

  • Main path — resume/rotate: re-attach 对同一 (serverId, attachedByUserId, name) 的现有 attachment（仍 live、未 revoked） → server 在原 computers row 上 rotate credential（hash 覆盖、旧 raw key 失效），CLI 收到 resumed=true。任务 #21 multi-attach 锁的就是这条：同一 user 用同一 name 重 attach 不创建第二行，也不当 collision。
  • Cross-user same displayName allowed: 不同 attachedByUserId 把自己机器都叫 "MacBook-Pro" 接到同一 server 是合法的 — collision tuple 含 user，跨 user 不互锁。
  • No displayName-collision error in current contract: same-user new-create with name conflict 在当前实现里不发生 — 同一 user 同一 name 命中走 resume/rotate（上面 main path），不走"create 新行 + collision"。packages/computer/src/attach.ts 含一段 defensive COMPUTER_NAME_COLLISION handler 作为未来产品演进的占位，但当前 server 不返回这个 code，validating tests / contract 不依赖它。任何引入 displayName-uniqueness 的未来变更必须在 v8.3+ 新轮 contract review 走流程，不能假设这条已经活着。

非 --adopt-legacy 路径下的处理（argv vs env 区分对待）：

  • argv flag --legacy-api-key / --legacy-api-key-file / --legacy-api-key-stdin 出现在不带 --adopt-legacy 的命令（裸 setup / attach / login）上 → 立即 fail-closed LEGACY_KEY_OUTSIDE_ADOPT（非零 exit + structured error），不静默忽略。理由：argv 是用户 主动 explicit input，silent-ignore 会制造 "我传了 key 但其实没用" 的假成功感（与 PR-G --target-version Commander shadow footgun 同类）。
  • env SLOCK_LEGACY_API_KEY 在不带 --adopt-legacy 的命令里继续保持非-ambient（被忽略），不报错。理由：env 可能来自 shell rc / systemd unit / .envrc，user 不一定知道存在，silent-ignore 是 safe-default；与 argv 主动输入性质不同。

统一原则：legacy-key path 只在明确 migration intent (--adopt-legacy) 下参与状态变更，绝不在旁路里悄悄变成 no-op 或 fresh attach。

5.11.2 Server-side semantics

Server POST /api/computer/adopt-legacy（USER-authenticated，与 device-code approve 同 trust boundary）接收 legacy key proof：

  • Legacy proof 命中：resolve 出对应 machines.id → 创建 / 恢复 computers row 并 computers.machineId = machines.id。旧 machines 行 保留（agents 与 runtime profiles 仍指向它，Computer 把它当作 orchestrator backing identity）。
  • Credential 一次性 mark：成功后 server 把旧 key 标记 machines.legacyKeyMigratedAt = now()。旧 sk_machine_* 之后对 /daemon/connect 和 /internal/computer/* 全部拒绝，返回 stable code legacy_machine_key_migrated（HTTP 409）。Contract 用语是 "revoke credential, not row"，不是 "delete machine"。
  • Atomic adoption commit：legacy key proof resolve + machines.legacyKeyMigratedAt mark + 新 sk_computer_* mint + computers row create/restore 必须在同一 transactional commit 内完成。Concurrent / repeated adoption attempt 同一 machines.id → 只有一次成功 mint，losers 一律返回 legacy_machine_key_migrated（409）或 adoption_conflict，不再 mint。Implementation 推荐 UPDATE machines SET legacy_key_migrated_at = now() WHERE id = $1 AND legacy_key_migrated_at IS NULL RETURNING ... + active-Computer-owner uniqueness guard，确保 single owner per legacy machine。
  • 重复 adopt：同一 key 第二次提交直接 legacy_machine_key_migrated（409），不再 mint。
  • Key 提供但 proof 失败（typo / wrong server / malformed / unknown key）：fail-closed，stable code legacy_key_invalid（HTTP 401），server 不 mint 新 sk_computer_*、不 创建 computers row、CLI 不 写 attachment.json。Adoption.log 仍记一行，credential_bridge_mode=<尝试过的 legacy_key_* channel> + failure_reason=legacy_key_invalid。避免用户以为 adoption 成功、旧 machine 实际被 strand。
  • 无 key channel 提供（用户 --adopt-legacy 但本地已经没旧 key，例如机器迁移过来只有 hostname）：明示 fallback 到普通 device-code login + 新 Computer attach。新 Computer 链接到新 machines 行；旧 machines 行 stranded / read-only。CLI 文案 "未找到旧 machine key，将以全新 Computer 身份注册"；adoption.log 记 credential_bridge_mode=device_login。Server-side cleanup of stranded legacy machine row 不在 v8.2 scope，单独 tracked。

Phase-1 兼容窗口（与 §10.5 一致）：sk_machine_* 仍可作为 /internal/computer/* alias，仅限 未经 adoption 的 machine。Adoption 之后 alias 立即按 legacy_machine_key_migrated 拒绝，不静默继续。

5.11.3 Schema and implementation requirements

实现 PR（不在本 contract PR 范围）必须包含：

  • Schema field：Drizzle / TS 模型字段 machines.legacyKeyMigratedAt；SQL column machines.legacy_key_migrated_at timestamptz null。Migration 脚本 + 本地 PostgreSQL 测试（与 team rule "DB schema changes require migration scripts + local testing" 一致）。
  • 认证路径检查 legacy_key_migrated_at IS NOT NULL 时 fail-closed。
  • Auth cache invalidation：server findMachineByApiKey in-memory auth cache 命中只返回 { machineId, serverId }、不重查 DB；adoption 成功设置 legacyKeyMigratedAt 的同一动作必须立即 invalidate 该 legacy key 的 cache entry，或让 cache lookup 路径携带 legacyKeyMigratedAt check。Post-adoption alias rejection 必须覆盖 "same process, previously cached key" case，不允许靠 TTL 自然过期兜底。
  • Raw legacy key 在任何路径下都 不 写入 attachment.json / status JSON / adoption.log / 常规 log / process argv 长留 / DB 列。Adoption 成功后从 process memory 抹除。

Old-daemon-process invariant:

  • Implicit fail-closed：setup / attach 检测到 legacy daemon pid 仍在跑（~/.slock/daemon.{pid,json}） → 返回 LEGACY_DAEMON_RUNNING，不静默 adopt。
  • Explicit adopt：slock-computer adopt / setup --adopt-legacy 由 adopt flow 负责停 legacy pid 并 verify（pid 实际退出 + 新 supervisor 持有唯一 lock），整个 lifecycle event 写 §5.11.4 adoption.log。

5.11.4 Adoption audit log

每次 adopt（不管成功 / 失败 / fallback）必须在 ~/.slock/computer/adoption.log 追加一行 forensic 记录：

2026-05-22T04:32:11Z legacy_pid=12345 legacy_pid_stopped_at=2026-05-22T04:32:08Z new_supervisor_pid=67890 new_supervisor_started_at=2026-05-22T04:32:10Z sk_computer_minted_at=2026-05-22T04:32:11Z credential_bridge_mode=legacy_key_file

credential_bridge_mode 是 closed enum，byte-精确：

credential_bridge_mode ∈ {
  device_login,
  legacy_key_argv,
  legacy_key_file,
  legacy_key_stdin,
  legacy_key_env
}

语义对仗：device_login 是 "no legacy credential bridge; fresh sk_computer_ minted from device-code login"；其余 4 个 legacy_key_* 都是 migration-only / deprecated channel。Aggregation 查询 "所有 legacy bridge" 用 LIKE 'legacy_key_%'。

Raw key 不进入 audit log；最多记录 redacted prefix（前 8 字符）或 HMAC surrogate mch_<hex>（与 PR #1329 raw-ID hygiene 一致：未来 trace surface carry 旧 machine 标识也只能用 surrogate）。

Attribute name lock：credential_bridge_mode 既是 audit-log 字段名，也是未来 lifecycle trace event（task #164 / §13 Q4 reserved credential lifecycle enum activation 时）的 trace attr 名。不允许 audit-log 用一个名、trace event 用另一个名。

5.11.5 Web "Add this Computer" command

Server 的 web UI 在生成"添加新机器"复制命令时区分两种 case：

  • New machine：npx @slock-ai/computer setup /<slug>，不带 legacy flag。
  • Old machine（用户在 web 上勾选 "从老 daemon 迁移"）：可生成 npx @slock-ai/computer setup /<slug> --adopt-legacy --legacy-api-key <key> 一行迁移命令。UI 必须明示 "this is a one-time migration command; after running, the old key will be invalidated"，且这条命令在迁移完成后失效 / 不重新生成。

Rationale（与 wg 决议一致）：legacy daemon 既有 contract 就是 --api-key argv，迁移日 shell history / process list 上这条 leak surface 已经存在，强行禁 argv 不能消除历史风险；务实边界是 "argv 不能成为长期 credential surface"，via §5.11.2 server 一次性 mark migrated + §5.11.4 audit log 收掉风险。User 偏好更安全 channel 时 file / stdin / env 三档随时可用。

6. Capability model

Runner capability 有两层：

authorized = credential.max_capabilities ∩ session.active_capabilities

含义：

  • max_capabilities 是 server mint credential 时给的上限。
  • active_capabilities 是当前 runner session 实际支持 / 开启的能力。

错误语义：

情况错误
capability 不在 credential max set403 capability_not_authorized
capability 在 max set，但当前 session 没有 active501 unsupported_capability
runner 离线runner_unavailable

不能因为 runner 不支持某项能力就 fallback 到 Computer。

实现上不能只把 scopes 塞到 req.agentCredentialScopes 后不检查。每个 handler 或统一 middleware 必须真的 enforce capability。

7.1 Runner transport

每个 Runner 应该有自己的 runner websocket / event stream。Computer 不能 multiplex agent data plane。

Computer / server session worker 可以报告 runner process 生命周期，但不能替 Runner 发送 agent event ack、read cursor、message send、task action。

7.2 catch-up 不走 send response

send response 不应该带 catch-up / recentUnread。

正确 catch-up path：

  • Runner websocket resume / push。
  • 或显式：

``text GET /internal/agent-api/events?since=... ``

不要把 send path 重新变成 inbox drain。send 是 action commit，不是收件箱同步。

7.3 managed / external transport equivalence

managed runner 可以主要依赖 websocket push；self-hosted runner 可以主要依赖 HTTP poll：

GET /internal/agent-api/events?since=...

这两条 transport 在三个轴上必须等价：

  • envelope schema。
  • ordering invariants。
  • projection semantics。

Managed runner 通过 daemon-local proxy 暴露 /internal/agent-api/events 时，projection 必须先尊重 daemon Local Inbox：只要 Local Inbox 有 pending message，events / slock message check 必须从 Local Inbox 返回并消费该 batch。远端 server /events 只能作为 Local Inbox 为空后的 sync / repair / fill 来源；远端返回的数据如需进入模型可见面，也必须先经过 Local Inbox / visible-consume 等价路径。

它们在 latency 上不要求等价。push 和 pull 的延迟差异是产品 capability 差异，不是 correctness bug。不能因为 self-hosted runner 用 HTTP poll，就给它另一套 wake envelope 或另一套 event semantics。

7.4 wake envelope

本 RFC 定义 wake envelope 的 transport 位置，但不拥有 wake_reason enum。

wake_reason 属于 task #164 Agent Lifecycle Event Model。任何 placeholder enum 都不能在未对齐 #164 的情况下 merge。

Wake envelope 里的 seen boundary 必须使用 model-seen 语义，和 0.50.0 send freshness gate 同源。不要用 delivery cursor / read cursor 代替 last_seen_msgId。delivery cursor 是 transport 实现细节；model-seen 才表达 agent model 实际覆盖到的上下文边界。

Phase 1: vertical slice

目标是证明 Agent Runner credential 和 /internal/agent-api/* 可以跑通，不要求立刻完成 process split 或立刻删除 legacy daemon entrypoint。

包含：

  • 5 个核心 agent routes。
  • catch-up events。
  • whoami / server。
  • agent credential mint / exchange。
  • 一个 Computer credential request endpoint。
  • legacy daemon entrypoint 可以临时启动 single-server session worker，并以 runner shim 方式运行：

``text --agent-key-mode=sk_agent ``

Phase 1 期间允许现有 sk_machine_* 作为 Computer principal alias 调 /internal/computer/*。这是迁移期事实，不是 daemon principal，也不是第二套长期 contract。

部署顺序要求 server-first：server 舰队必须先全量带上 /internal/computer/* credential mint 端点，再发布新版 daemon。新版 daemon managed runner mint 失败时 hard-fail agent start，不在进程内降级到 legacy /internal/agent/:id/*；回滚新版 daemon 二进制是 release safety 手段。

Phase 1 不允许：

  • sk_machine_* 调 /internal/agent-api/*。
  • Computer 代 agent 调 data plane。
  • runtime child 看到 sk_agent_*。
  • send response 带 catch-up。

Phase 1.x: complete API surface

扩展到完整 28 个 /internal/agent-api/* capability routes。

补齐 Computer surface：

  • heartbeat。
  • self。
  • server attachment session state。
  • runners list。
  • runner started。
  • runner exited。
  • credential request。

Phase 2: introduce Computer core and server session worker

新增 / 明确 slock/computer core 作为 runner 之外的本机 control plane：

Computer control plane
  -> server session worker(s)
  -> agent runner(s)

旧 @slock-ai/daemon package / command 保留为 compatibility launcher：内部启动 single-server Computer session，但不再承载新产品语义。

Phase 3: process split

抽出真正的 @slock-ai/agent-runner 或等价 runner wrapper。

Computer control plane 负责 multi-server attachment 和 supervision。Server session worker 负责 per-server connection / event routing。Runner 打开自己的 runner websocket，并用 sk_agent_* 调 /internal/agent-api/*。

Phase 4: remove legacy machine-on-behalf

删除或关闭：

/internal/agent/:id/*

machine-on-behalf 不再是 agent data plane。

Phase 5: credential prefix rename

把 sk_machine_* 迁移为：

sk_computer_*

迁移窗口内可以同时接受旧 prefix，但必须有结束策略。

Phase 6: retire legacy daemon entrypoint

等 slock/computer、multi-server attachment、desktop shell 和 self-update 路径稳定后，再把 legacy daemon package 变成 permanent thin wrapper 或正式 deprecate。

  4. runner 可以通过 /internal/agent-api/*：
  • send message。
  • claim task。
  • react。
  • read catch-up events。
  1. audit log 显示 agent credential，而不是 human JWT 或 Computer credential。

10.2 Managed runner acceptance

managed path 在 single-server session worker / compatibility daemon mode：

  1. Computer 用自己的 Computer credential 请求 runner credential。
  2. server mint managed-runner sk_agent_*。
  3. Computer / server session worker 在 daemon 进程内私有持有 key。
  4. wrapper / CLI 只通过本地 proxy / IPC affordance 调用 Slock，不接触 raw bearer key。
  5. mint 成功路径不再写入或注入 legacy machine token；mint 失败在 bounded retry 后 hard-fail agent start，并记录 runner_credential_mint_failed 类 trace/error，不写 legacy SLOCK_AGENT_TOKEN_FILE。
  6. runtime CLI child、tool shell、workspace exec 看不到 raw key，也看不到可读 raw-key file pointer。
  7. server session worker 在 runner stop/exit 时 unregister local proxy，并对 managed-runner credential 发起 best-effort revoke；revoke 失败必须 trace，launch-bound TTL / server reaper 作为后续自愈项。
  8. chat bridge 通过 /internal/agent-api/* send / task / react。
  9. audit log 显示 sk_agent_*。

SLOCK_EXPERIMENTAL_SURFACES_DISABLED 是 v0.8 surface 的 hard-disable / kill switch：打开后新版 daemon managed runner startup 必须失败，运维应回滚 daemon 二进制，而不是期待 graceful legacy fallback。

10.3 Key isolation acceptance

目标态必须有测试证明：

  • runtime child env 中没有 raw sk_agent_*。
  • runtime child env 中没有任何可读 raw-key file pointer。
  • mint success path 中 runtime child env / workspace 没有 SLOCK_AGENT_TOKEN_FILE 或 legacy machine-token 文件。
  • tool shell / workspace exec / additional MCP subprocess 读不到 raw sk_agent_* 或 legacy machine token。
  • CLI 如果需要 Slock 操作，走 wrapper local proxy affordance；proxy 无条件覆盖 active-capability header，不信任 caller 输入。
  • local proxy token 在 runner launch stop/exit 后失效。
  • managed-runner 底层 sk_agent_* 在 runner launch stop/exit 的成功 revoke 路径后，直打 /internal/agent-api/* 返回 401；revoke 失败路径必须 trace/audit，强自愈留给 TTL/reaper follow-up。

只证明“raw env 不存在”不够。如果 mint success path 仍然留下 legacy machine token，或 proxy/managed credential 不随 launch 失效，也算失败。

  • CLI slock-computer login 优先打印 verificationUriComplete，无则打印 verificationUri + 单独 Enter code: 行；CLI 不把 server 返回的 relative path 用 baseUrl 拼接，遇到非绝对 web URL 立即 fail-closed DEVICE_LOGIN_URL_UNAVAILABLE。
  • web /login/device 页面接受 user_code query 预填，approve 路径用 POST /api/auth/device/approve。

10.13 Legacy daemon adoption acceptance

v8.2 narrow append。Adoption 流程验收要求：

  • Happy path：slock-computer setup /<slug> --adopt-legacy --legacy-api-key <key>（或 --legacy-api-key-file / --legacy-api-key-stdin / SLOCK_LEGACY_API_KEY env 任一）成功 → server 标记 machines.legacyKeyMigratedAt = now()，mint 新 sk_computer_*，CLI 写入 attachment.json。~/.slock/computer/adoption.log 追加一行含 credential_bridge_mode= 对应 enum 值的记录。
  • 重复 adopt：同一 legacy key 第二次提交（key 本身仍 valid，但 legacyKeyMigratedAt 已 set） → server 直接返回 legacy_machine_key_migrated（HTTP 409），不再 mint。adoption.log 记 credential_bridge_mode=<尝试过的 legacy_key_* channel> + failure_reason=legacy_machine_key_migrated。不要把这桶 collapse 进 legacy_key_invalid：repeat-adopt 表示用户已经迁过，再点是 cross-host reuse 或 client-side state 失同步；invalid-key 表示 typo / wrong server / 真错 key — 处置路径不同，observability 必须分流。
  • Post-adoption alias 拒绝：被 mark migrated 的 sk_machine_* 调 /daemon/connect 或 /internal/computer/* → 返回 legacy_machine_key_migrated（401 / 403 / 409 视路径而定，文案稳定）；不静默继续 Phase-1 alias 行为。
  • Auth cache invalidation：adoption 成功设置 legacyKeyMigratedAt 后，server 在同一动作内 invalidate findMachineByApiKey auth cache 中该 legacy key 的 entry（或让 cache lookup 携带 legacyKeyMigratedAt check）；同一 server process 在 adoption 后立刻用同一 cached legacy key 调 /daemon/connect / /internal/computer/* 必须立即返回 legacy_machine_key_migrated，不允许靠 cache TTL 自然过期兜底。
  • Implicit fail-closed：legacy daemon pid 仍在跑而未传 --adopt-legacy → CLI 返回 LEGACY_DAEMON_RUNNING；不静默 adopt 也不静默 fresh attach。
  • Explicit adopt 终态：--adopt-legacy 路径 verify 旧 pid 退出 + 新 supervisor 持有唯一 lock + sk_computer_ minted；任一缺失 → adoption 失败、不写 attachment.json、adoption.log 仍记一行带 failure reason。
  • Outcome A — no key channel provided：setup --adopt-legacy 未传任何 --legacy-api-key* flag 也没 SLOCK_LEGACY_API_KEY env → CLI 明示降级走普通 device-code login + 新 Computer attach；CLI 文案 "未找到旧 machine key，将以全新 Computer 身份注册。旧 machine 记录在 server 端的处理由 server 决定。" adoption.log 记 credential_bridge_mode=device_login。
  • Outcome B — key provided but invalid（typo / wrong-server / malformed / unknown）：server 返回 legacy_key_invalid（401），不 mint 新 sk_computer_*、不 创建 computers row、CLI 不 写 attachment.json。adoption.log 记 credential_bridge_mode=<尝试过的 legacy_key_* channel> + failure_reason=legacy_key_invalid。CLI 退出非零，文案明示 "legacy key 无效，未注册新 Computer"，绝不静默 fresh-attach。
  • Outcome C — concurrent adoption same legacy machine：两个并发 POST /api/computer/adopt-legacy 同一 machines.id → 恰有一个 transaction commit 成功 mint，loser 一律返回 legacy_machine_key_migrated（409）或 adoption_conflict，绝不 double-mint、绝不出现两个 active Computer 同时绑定同一 machines.id。Loser 的 CLI 不写 attachment.json，adoption.log 仍记一行带 failure_reason=adoption_conflict。
  • Stray legacy flag rejection：--legacy-api-key* flag 出现在非 --adopt-legacy 命令（如裸 setup / attach / login）→ CLI 立即以 LEGACY_KEY_OUTSIDE_ADOPT 报错退出，不静默忽略。SLOCK_LEGACY_API_KEY env 在非 --adopt-legacy 命令保持非-ambient（被忽略），不报错；ignored env value 不读入 process memory、不进任何 log / status / error / adoption.log 字段，保留 dotfile / shell rc / systemd unit / .envrc 残留兼容性。
  • Raw key hygiene：raw legacy key 不出现在 attachment.json / status JSON / adoption.log / 常规 log / process argv 长留 / DB 列。adoption.log 最多记 redacted prefix（前 8 字符）或 HMAC surrogate mch_<hex>。
  • Schema migration：实现 PR 包含 SQL column machines.legacy_key_migrated_at timestamptz null（Drizzle / TS 模型字段 legacyKeyMigratedAt）migration 脚本 + 本地 PostgreSQL 测试。
  • Enum byte-lock — credential_bridge_mode：严格 ∈ {device_login, legacy_key_argv, legacy_key_file, legacy_key_stdin, legacy_key_env}，5-value closed set，snake_case，无变体（如 device-login / legacyKeyFile 必须被 review 拒绝）。Audit-log 字段名与未来 trace attr 名同形。
  • Enum byte-lock — failure_reason：adoption.log 中 failure 行的 failure_reason 字段严格 ∈ {legacy_key_invalid, legacy_machine_key_migrated, adoption_conflict}，3-value closed set，snake_case，与 outcome 桶 1:1：
    • legacy_key_invalid ← Outcome B（typo / wrong server / malformed / unknown key — server auth fail）
    • legacy_machine_key_migrated ← 重复 adopt（key valid 但 legacyKeyMigratedAt 已 set — cross-host reuse / 客户端状态失同步）。注意：与 server-side stable code 同名同形（HTTP 409），由 adopt.ts 的 failureReason 字段直接写入 adoption.log。
    • adoption_conflict ← Outcome C（并发 race，loser）
    不允许把 invalid 和 migrated collapse 成一个常量；observability 必须能区分 user-typo / cross-host reuse / concurrent adopt 三条 path。Audit-log 字段名与未来 trace attr 名同形。

10.14 Upgrade contract acceptance

v8.3 narrow append。slock-computer upgrade（CLI / web / tray 任一触发）验收要求：

  • Atomic install (pre-commit)（v8.3.3 cleanup — atomicity 限 stage→swap 边界内；post-commit no rollback）：upgrade 触发对一个 computer@0.0.4 + daemon@0.52.0 的 Computer service → swap committed 后到 computer@0.0.5 + daemon@0.53.0 是同一 atomic transaction；不允许观察到 computer@0.0.5 + daemon@0.52.0 的半 swap 中间态。Pre-swap 失败注入（network/integrity/swap） → active layout 仍 prior（详见后续 stage-fail / swap-fail acceptance items）。
  • Bounded sequential restart (blast-radius)（v8.3.3 rename，blast-radius framing 替代 rolling availability framing）：upgrade 在有 N≥2 active agent runner 的 Computer service 上运行 → restart 必须串行（v0 = 1-at-a-time）；每个 runner restart 等到 replacement 上报 running_idle lifecycle event 才 kill 下一个；READY_WAIT_TIMEOUT_MS = 30000。Synthetic test 断言：upgrade 期间任意时刻 本 Computer service 管理的 agent runner 中不允许两个同时处于 activityKind=starting（scope = blast-radius / 资源约束限定于本 Computer service 管理面，不是 rolling availability guarantee；不跨 Computer 全局序列化）。
  • Stage-fail cleanup (pre-swap)（v8.3.3 cleanup — Hao 两概念拆分的"不提交"侧）：synthetic test 注入 stage phase 失败（network / integrity / deps_changed） → 验：(i) emit 对应 closed-set error（UPGRADE_NETWORK_FAILED / _INTEGRITY_FAILED / _DEPS_CHANGED）；(ii) active layout 未触碰；(iii) GET /api/computers/:id 的 computerVersion 仍 prior（forensic bundledDaemonVersion 也 prior）；(iv) staging artifact 保留在 upgradeStagingDir(version)（与 PR #2080 paths.ts same-version retry semantics 一致；不自动删，operator 检查 forensic 后手动 rm -rf 才解锁同 version retry）。所有 path 走 paths.ts::upgradeStagingDir(version)，实现代码 grep 不出字面量。
  • Swap-fail (pre-commit, atomic rename failure)（v8.3.3 cleanup）：synthetic test 注入 atomic swap 失败（rename(2) / MoveFileEx error） → 验 emit UPGRADE_SWAP_FAILED + active layout 未触碰（lock 屏蔽规则下，半 swap state 不可观察） + computerVersion 仍 prior + status human text 仍显 prior version；零 disruption。
  • Restart-fail (post-commit, no reverse-swap)（v8.3.3 cleanup — Hao + Adspectum + Cody lock no-rollback contract）：synthetic test 注入第 K 个 runner（1 ≤ K ≤ N）replacement 不上报 running_idle 至超时 → 验：(i) emit UPGRADE_RESTART_FAILED；(ii) 不 reverse-swap，不 kill 已 restart 跑在新 layout 的 runner；(iii) computerVersion = new（已 committed forward-only）；(iv) Computer service status 标 unhealthy；(v) actionable hint emit 引导 `slock-computer restart` / 人工 inspect / 重跑 `upgrade`。Post-commit no-rollback invariant：任何 reverse-swap / `.prev` 恢复 / 已切 runner kill 行为 → fail；contract = "active layout 一旦 swap 即 committed forward-only"。
  • In-flight turn / tool call 不保护：bounded sequential restart 期间若 runner 正在 in-flight turn / tool call，supervisor 仍按 ready-wait timeout 推进，不为该 turn 留 grace；中断 agent 通过 Slock inbox replay + workspace MEMORY.md/notes 恢复。Synthetic test：runner 当前 turn 中向 chat-bridge 发送中 → restart 触发 → 验 turn 被中断但 agent 在 replacement runner 上从 inbox 看到原 wake event 并恢复处理（与 PR #2068 runtime switch reset-session 同 acceptance shape）。
  • Single version display — API（v8.3.2 cleanup）：GET /api/computers/:id response 包含 computerVersion: string（非空 primary surface）。Optional forensic field bundledDaemonVersion: string 可缺省；若 emit，字段名 必须 是 bundledDaemonVersion，禁 任何字段叫 daemonVersion primary（消费者会误读为 UI contract）。
  • Single version display — CLI（v8.3.2 cleanup）：slock-computer status human text 输出单行 Computer service: <ver>；--json 输出包含 computerVersion + forensic bundledDaemonVersion。Bundled daemon version 不出现在 status human text 的必显内容里（debug field marker 允许）。
  • Single version display — Web（v8.3.2 cleanup）：Computer 详情页 metadata block 单行渲染 Computer service 版本号；不允许把 bundled daemon version 升到 primary 渲染面 → e2e fail。
  • Bundled daemon version forensic-only invariant（v8.3.2 cleanup）：上 3 个 surface 加 tray status submenu 共 4 个 user-facing surface 全部 grep bundledDaemonVersion 字段：仅 --json 输出 / upgrade.log 行 / `[forensic]` marker 内 context 可出现；任何在 human text / web metadata primary / tray menu primary 暴露 bundled daemon version 的 codepath → fail。
  • upgrade target resolution single-axis（v8.3.2 cleanup）：synthetic test 注入"Computer 0.0.6 已是 channel latest 但 bundled daemon dep 在内部 bumped 到 0.54.0" → 验 CLI 输出 "Already at 0.0.6 (channel latest). Nothing to do."，不 触发 "daemon needs upgrade" 信号；bundled daemon dep 变化必须靠新 Computer bundle ship 才传播，不单独构成 upgrade-available 状态。
  • Trigger source convergence：CLI slock-computer upgrade、web "Upgrade" 按钮 click、tray "Upgrade" 项 click 三种 trigger 触发同一 backend upgrade RPC；upgrade.log entry 字段除 trigger ∈ {cli, web, tray} 外完全相同。
  • Channel pinning：
    • slock-computer channel pinned:0.0.5 后 upgrade → 即便 latest 更高，也只装 0.0.5。
    • slock-computer channel pinned:notsemver 或 channel garbage → 立即返回 CHANNEL_INVALID（v6 §11 既有 stable code），channel state 不变。
    • Channel state 在 Computer service 重启后保留。
  • Failure mode closed-set（v8.3.3 cleanup — 7-value，delete `UPGRADE_ATOMIC_ROLLBACK` + add `UPGRADE_SWAP_FAILED` / `UPGRADE_RESTART_FAILED` via RFC bump per §4.4 (6)）：所有 7 个 error code（UPGRADE_DEPS_CHANGED / UPGRADE_NETWORK_FAILED / UPGRADE_INTEGRITY_FAILED / UPGRADE_SWAP_FAILED / UPGRADE_RESTART_FAILED / UPGRADE_NO_TARGET / UPGRADE_ALREADY_RUNNING）必须是稳定 SCREAMING_SNAKE_CASE 字符串字面量；CLI fail-path 各分支 emit 对应 code。Synthetic test 逐个注入故障 → 验 CLI 退出非零 + upgrade.log 记录正确 errorCode。Pre-commit vs post-commit boundary：前 4 code（DEPS / NETWORK / INTEGRITY / SWAP_FAILED）= pre-commit，active layout 未触碰、user 面 version 仍 prior；RESTART_FAILED = post-commit，active layout 已 new but unhealthy，无自动 reverse-swap。Closed-set discipline：additive-only；现有 value rename / delete 同等禁止；新增 8th value 必须 RFC bump。本 7-value 集限于 upgrade attempt outcomes —— pre-condition rejection codes（UPGRADE_REQUIRES_ADOPTION / CHANNEL_INVALID，后者沿用 v6 §11 既有 stable code，非 v8.3 新增）与 informational codes（LEGACY_DAEMON_INSTALL_DETECTED）是独立 closed-set，不并入本集。
  • Concurrent upgrade：两个 simultaneous slock-computer upgrade → 恰一个获 lock 继续，另一个立即返回 UPGRADE_ALREADY_RUNNING；不允许 double upgrade 或 race 安装到不一致版本。
  • Web "Upgrade" button：
    • 始终可见。无更新可用（当前 channel 版本号 = latest）→ 按钮灰掉 + label "Up to date"。
    • 有更新可用 → 按钮 active，click → <ConfirmDialog> with brutal-orange confirm；cancel → no-op。
    • Confirm → 调用同一 backend upgrade RPC，同步 stream progress 状态给前端（progress / done / err）。
  • Web "Restart daemon" button（与 Upgrade 同 surface，sibling primitive）：
    • 始终可见，不带 confirm dialog。
    • Click → 立即 trigger restart；按钮转 <Spinner> loading 状态。
    • Restart 等 daemon reconnect 后清 loading；reconnect timeout → 露 error 状态。
    • Restart trigger 受 task #45 wakeability 修保护：active agent runner 不被 strand。
  • Activity log integration：成功 upgrade 在 Computer 详情页 activity tab 出现 system event "Computer upgraded from <fromComputer>/<fromDaemon> to <toComputer>/<toDaemon> via <trigger>"；失败 upgrade 出现 "Computer upgrade failed: <errorCode>"。
  • Backward compat — pre-bundled：Computer service 是 0.0.4 pre-bundled-daemon 形态 → 第一次 upgrade 安装两个包到新 layout，遗留 npm-installed daemon path 不动；doctor 报 LEGACY_DAEMON_INSTALL_DETECTED informational + cleanup hint。
  • Adoption boundary：未走 v8.2 §5.11 adopt-legacy 流程的 legacy daemon 调用 slock-computer upgrade → 立即 UPGRADE_REQUIRES_ADOPTION，不进入 install path。
  • Secret hygiene：sk_computer_* / sk_machine_* / sk_agent_* / API key / npm token 都不能出现在 upgrade.log 任何字段；npm 原始输出如需保留走单独 upgrade-install-<timestamp>.log，文件权限 0o600。

11. Hard non-goals

原 v0.8 §11 中 credential / auth / workspace / lifecycle producer 子集（条目 1–11）已 verbatim 抬到 slock-credential-rfc.zh.html §6 Hard non-goals (credential subset)（base RFC v0.1），本文不再维护。

Computer-specific 不在 v0.1 内、且不应该被实现成临时捷径的事项（编号沿用原 v0.8）：

  1. (v8.3) Upgrade bounded sequential restart 期间保护 in-flight turn / tool call。不承诺 live migration —— bounded sequential restart 会中断当前 turn，agent 通过 Slock inbox replay + workspace MEMORY.md/notes 恢复（与 #proj-daemon PR #2068 runtime switch = session reset 模型同向）。任何为 in-flight turn 引入 grace window / drain protocol / mid-turn handoff 都属于此非目标，实现 PR review 应直接拒绝。
  2. (v8.3.3) Post-swap automated rollback machinery。一旦 atomic swap commit 完成，active layout 是 forward-only committed 到新 bundle；后续 restart / runner ready 失败 = fail-loud + Computer service 标 unhealthy + actionable hint 引导 user 手动 recovery（slock-computer restart / 人工 inspect / 重跑 upgrade）。任何 reverse-swap / `.prev` 自动恢复 / snapshot 状态文件读 prior / 自动 kill 已切 runner 切回旧 layout 都属于此非目标，实现 PR review 应直接拒绝。Recovery 是 user 主动行为，不是 contract 自动事务保证。Hao msg=aee2822d 两概念拆分（保留 staging fail-cleanup pre-swap，删 post-swap rollback）一致 lock。

13. Closed decisions

  1. Self-hosted Runner 和 Managed Runner 使用同一套 Agent Runner API。
  2. Agent Runner API 是 /internal/agent-api/*，identity 来自 sk_agent_*，path 不带 :id。
  3. Computer API 是 /internal/computer/*。
  4. Server session worker 不是 principal，不进 lifecycle producer table。
  5. Legacy daemon package / command 只作为 compatibility launcher。
  6. Computer 不能本地 mint agent credential。
  7. Computer / server session worker 不能代 agent 调 agent data plane。
  8. Workspace belongs to Runner。
  9. Capability enforcement 是 max_capabilities ∩ active_capabilities。
  10. wrong principal 用 invalid_principal，cross-agent 用 cross_agent_act。
  11. send response 不做 catch-up。
  12. wake envelope last_seen_msgId 使用 model-seen 语义。
  13. runner key isolation 是 release gate，不是 best effort。

14. Implementation checklist for PR review

PR 进入 review-ready 前，至少要逐项回答：

  • [ ] /internal/agent-api/* 是否只接受 sk_agent_*？
  • [ ] /internal/computer/* 是否只接受 sk_computer_* 或 Phase 1 alias sk_machine_*？
  • [ ] sk_machine_* 是否被禁止调用 /internal/agent-api/*？
  • [ ] agent A 是否不能 acting as agent B？
  • [ ] route auth registry 是否真的 mounted？
  • [ ] 未注册 internal route 是否 fail closed？
  • [ ] read-only agent credential 是否无法 send / mutate task / react？
  • [ ] inactive session capability 是否返回 unsupported_capability？
  • [ ] runtime child env 是否完全 scrub raw credential env？
  • [ ] runtime child 是否无法通过 raw-key file pointer 读到 sk_agent_*？
  • [ ] mint success path 是否不写入/注入 legacy machine token 或 SLOCK_AGENT_TOKEN_FILE？
  • [ ] mint failure 是否 bounded retry 后 hard-fail，且不写 legacy token / 不进入 legacy-machine clientMode？
  • [ ] proxy 是否无条件覆盖 active-capability header？
  • [ ] local proxy token 是否绑定 launch，并在 stop/exit 后 401？
  • [ ] managed-runner 底层 sk_agent_* 是否在 stop/exit 的成功 revoke 路径后 401，且 revoke 失败路径有 trace/audit hook？
  • [ ] managed runner 是否能在只有 legacy host credential 的 Phase 1 compatibility entrypoint 环境请求 runner credential，且 server-first / daemon rollback 是 release safety 机制？
  • [ ] server session worker 是否没有独立 principal / credential / lifecycle producer 语义？
  • [ ] self-hosted runner direct credential path 是否保留同一套 Agent Runner API，且 bootstrap/login 外部 surface 默认 gated off？
  • [ ] send response 是否没有 catch-up unread payload？
  • [ ] wake envelope 的 seen boundary 是否和 send freshness 一样是 model-seen？
  • [ ] /internal/agent-api/server 是否没有 machine identity leakage？

如果这些问题中任何一个答案是否定的，PR 还没有实现 v0.8 的最小安全边界。
