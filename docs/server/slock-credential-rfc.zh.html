1. Credential 模型

本节内容 lifted verbatim from Computer RFC v8.3.3 §3 (Credential 模型, §3.1-§3.4)。语义不变；renumber 仅为本文档内部组织。

1.1 credential 类型

Credential主体作用域典型 API
user JWTHumanuser / org / server/api/*
sk_computer_*Computer server attachment单 Computer + 单 server attachment/internal/computer/*
sk_agent_*Agent Runner process单 agent + capabilities/internal/agent-api/*

sk_computer_* 不是 account-level computer identity，也不是 server session worker identity。它表示"这台 Computer attach 到这个 server 的一段身份"。同一台物理机器 attach 到 N 个 server，会得到 N 份 Computer credential，由 Computer control plane 做本地 credential storage 和 attachment routing。

1.2 server 是唯一 mint authority

Computer 不能本地 mint runner credential。正确说法是：

  • Computer requests a runner credential from the server.
  • Server mints an sk_agent_*.
  • Computer hands it to the runner wrapper.
  • Runner starts with that key.

不要把这个过程写成 Computer-mint。Computer 只是 authorized requester，不是 local CA。

1.3 一个请求，一个 principal

Computer host 作为本机 control plane 可以管理多个 server attachment，因此同一个长期 Computer process 可能持有多份 server-scoped sk_computer_*。这不意味着一个 HTTP/WebSocket 请求可以混用身份。

规则是：

  • 每个 outbound control-plane request 必须选择一个明确的 server attachment，并只使用对应的 sk_computer_*。
  • Server session worker 运行在某个 attachment 下；它没有自己的 credential，也不能跨 attachment 复用 credential。
  • Runner process 的 agent data-plane 只能通过 managed local proxy 或 self-hosted runner credential 代表一个 agent。它的生命周期内只代表这个 agent runner。

不支持 live key switching：

  • Runner 要换 agent：退出并重新 spawn。
  • Runner 要 rotate credential：退出并重新 spawn。
  • Server session worker 要切 server attachment：退出并重新创建。

这个规则让审计、权限和故障恢复简单：一个外部行为只能归属一个 principal。Computer 可以管理多个 attachment，但不能在同一个 request / session / runner handoff 中混用多个 principal。

1.4 runner key isolation

sk_agent_* 是最高风险边界之一。plaintext sk_agent_* 只能出现在：

  • runner wrapper 的私有内存 / 私有配置。
  • chat bridge 的私有调用层。
  • 专门的 runner private env。

不得出现在：

  • runtime CLI 子进程环境变量里。
  • tool shell 环境变量里。
  • workspace exec 环境变量里。
  • additional MCP subprocess 环境变量里。
  • workspace 可读文件里。
  • runtime 能通过 env 指针读到的 0600 key file 里。

wrapper 必须 scrub 所有 SLOCK_* 相关 env，再启动 runtime CLI 和 tool shell。

如果在 runtime shell 里执行 echo $SLOCK_AGENT_KEY 能看到 key，这是架构 bug。 如果 runtime shell 里能通过任何 file pointer 读到 raw agent key，这也是架构 bug。 CLI 或 tool 如果需要调用 Slock，必须通过 wrapper 提供的本地 IPC / MCP affordance，而不是直接拿 bearer key。

v0.1 managed runner 的实现要求是：server session worker 在 daemon 进程内私有持有 sk_agent_*，本地 slock wrapper 只拿 launch-scoped local proxy / IPC affordance。runtime child、tool shell、workspace 文件和 wrapper 脚本都不能包含 raw bearer key、legacy machine token，或可读 raw-key file pointer。

注意：在现有 same-uid runtime/tool-shell 模型下，文件权限本身不是隔离边界；tool shell 能做 wrapper 能做的事。v0.1 接受的实际边界是 local proxy：proxy token 必须是 launch-scoped、capability-narrowed、可 revoke、可 audit，并由 daemon/server 侧强制覆盖 active capabilities。managed-runner 底层 sk_agent_* 在正常 stop/exit 路径上发起 best-effort revoke，失败必须留下 trace/audit hook；失败自愈（例如 launch-bound TTL 或 server reaper）是后续工作，不在本 PR 内声明为强保证。若要让 tool shell 完全触达不到任何 proxy secret，需要未来引入独立 uid / sandbox / process boundary，不属于本 PR。

2. API auth surface (generic)

本节内容 lifted from Computer RFC v8.3.3 §5.1-§5.5（generic auth axis）。Computer-specific 部分（§5.7-§5.11 status / display name / setup / device-login / legacy adoption）留 Computer product RFC。语义不变；renumber 仅为本文档内部组织。

Route auth policy 的形状用图说明：principal × path 必须 fail-closed。具体 principal type 名（sk_computer_* / sk_agent_*）由 §1 定义；具体 surface prefix（/internal/computer/* / /internal/agent-api/*）由下面 §2.1 / §2.2 给出。

2.1 Computer surface（举例 — 由 Computer product RFC 持有）

Canonical prefix:

/internal/computer/*

用途由 Computer product RFC §5.1 持有（host lifecycle / heartbeat / capacity / runner spawn-stop / runner credential request / runner list / state report 等）。本节只做 cross-product reference 的 anchor，具体 endpoint 列表不重复展开。

Only sk_computer_* 可以 call 这个 surface（Phase 1 sk_machine_* alias 见 Computer product RFC §10.5）。Server session worker 因为运行在 Computer attachment credential 下而能调用，本身不是单独 principal。

2.2 Agent Runner surface

Canonical prefix:

/internal/agent-api/*

这个 prefix 是长期设计，不计划改成裸 /agent-api/*。

/internal/agent-api/* 不带 :id。Agent identity 来自 bearer sk_agent_*，不是 path 参数。

这个 surface 包含 agent 行为（不 exhaustive）：server / whoami；read channel / thread / event catch-up；send message；update / send draft path；claim / unclaim / update task；react；reminders；profile；channel / thread follow state；action card prepare；workspace capability RPC。

Only sk_agent_* 可以 call 这个 surface。这个 surface 跨产品域共享（Computer-managed runner / self-hosted runner / future Login-with-Slock 第三方 agent runner 都使用同一套 Agent Runner API）。

2.3 Legacy machine-on-behalf surface

Legacy prefix:

/internal/agent/:id/*

这是 machine-on-behalf 模型，应被迁移掉。它不应该继续扩展，也不应该作为 self-hosted runner 的 API。

Phase 1 只把它作为旧版 daemon / compatibility client 的 legacy surface 保留。新版 managed runner mint 失败时不能把它当作 fallback；失败安全网是 server-first 发布和新版 daemon 二进制回滚。

2.4 Wrong-principal semantics

Wrong principal 要 fail closed，并且错误码稳定：

请求结果
sk_machine_* 调 /internal/agent-api/*401 invalid_principal
sk_agent_* 调 /internal/computer/*401 invalid_principal
sk_agent_* 调 /internal/machine/*401 invalid_principal
sk_computer_* 调 /internal/agent-api/*401 invalid_principal
agent A credential 试图 acting as agent B403 cross_agent_act

auth_policy_unregistered_path 只用于"这个 route 没有注册 auth policy"。它不是 wrong-principal 错误。

2.5 Server route auth policy

每个 internal route 都要有明确 auth policy。不能只写一个 registry 然后不 mount。

验收要求：

  • route auth registry 是实际执行路径的一部分。
  • 未注册 internal route fail closed。
  • wrong principal 回 invalid_principal。
  • cross-agent 回 cross_agent_act。
  • 测试覆盖 Computer surface、Agent Runner surface、legacy surface。

3. Server identifier (slug) surface

本节内容 lifted verbatim from Computer RFC v8.3.3 §5.6。Slug rebind lifecycle 跨产品域共享（Computer / self-hosted-agent / future Login-with-Slock 都需要同一套 slug 解析与 rebind 语义），lift 到本 base RFC；具体存储路径（如 attachment.json / computers.serverId）在引用本节的产品 RFC 中给出。语义不变。

Server 在 user-facing 面用 slug 而不是 UUID 识别。slug 是产品可见的唯一标识（web UI / URL 都是 slug），UUID 是 resolve 之后的内部 canonical id。

3.1 Canonical / shorthand

  • User-facing canonical form: /<slug>（与 @<handle> 平行）。
  • Bare <slug> 作为 shorthand input 接受；display 永远渲染 /<slug>。
  • UUID-shaped 输入 不 作为 compat alias，被视为 slug 并 fail-closed NOT_ATTACHED。错误文案不能泄露 "server id" / "UUID" 字样。

3.2 Wire shape

  • Computer attach surface（举例，由 Computer product RFC §5.1 / §5.6 持有）：request body 使用 serverSlug；response 同时返回 serverSlug（bare）和 serverId（UUID）。
  • Computer preflight surface（同上）：response 包含 serverSlug（bare），由 principal 绑定的 serverId 推导。
  • Server 侧 trust boundary（举例 computerCredentialService.attachComputer）解析 slug → serverId；DB row 与 computers.serverId 等 ownership 列保持 UUID。

同型 wire 适用于 self-hosted-agent / future Login-with-Slock 第三方 agent 接入路径。每个 product RFC 列出自己的具体 endpoint。

3.3 Storage（bare-only invariant）

  • Local-state file 中的 serverSlug 字段（举例 attachment.json#serverSlug）存 bare 形式（与 servers.slug DB 列、wire format 一致）。
  • / 是 render-layer 关注点，统一由 formatServerSlugDisplay(slug) 在 user-facing 字符串中加上。所有写本地状态的 callsite 写 bare。
  • 磁盘目录布局 keyed by UUID（举例 servers/<serverId>/）。Slug rename 不 移动本地状态。

3.4 Rename invariance（rebind lifecycle）

  • Server admin rename slug 后，本地 stale slug 命中 miss 时由 refreshAttachmentSlug-style helper 走 preflight，把 fresh slug 写回本地 state（bare），retry 命中同一 UUID-keyed 目录。
  • Credential / pid / log 状态目录因此与 slug 解耦，rename 不等于 detach + re-attach。
  • Self-hosted-agent --replace rebind（self-hosted RFC 任务 #9）使用同一套 rebind primitive：UUID-keyed identity, slug-presented surface, server-mint authority。两侧 must import same constant set，不 string-duplicate；parity test 跨两层。

3.5 Normalize（single point）

  • Single helper（举例 serverState.ts::normalizeServerSlug(input)）：strip ONE leading / + trim。alpha ≡ /alpha ≡ /alpha 。Multi-slash / 完整路径 fall through（不再继续 strip）。
  • 所有 selector entry point 必须经过此 helper。不能在调用方做局部 normalize。

4. Workspace ownership

本节内容 lifted verbatim from Computer RFC v8.3.3 §8。语义不变；renumber 仅为本文档内部组织。Workspace ownership 是 agent runner / agent data plane 通用语义，跨产品域共享（self-hosted runner 与 Computer-managed runner 同一规则），属 base RFC。

Workspace belongs to Runner.

这条规则意味着：

  • Runner 创建和拥有 agent workspace。
  • Runner 执行 workspace RPC。
  • Runner 决定当前 workspace capability 是否 active。
  • Server 对 workspace 的请求必须路由到 Runner。
  • Computer 不能作为 workspace fallback。

如果 Runner 不在线：

runner_unavailable

如果 Runner 在线但能力不存在：

unsupported_capability

如果 credential 没授权：

capability_not_authorized

这三个错误不能混用。

这三个 error code 是 base RFC 注册项，按 §5 stable error-code framework 流程治理（additive-only / rename = delete / 新 failure mode 必须走 RFC bump）。

5. Stable error code framework

本节是 framework-only meta-contract，描述跨产品域稳定错误码的注册 / 命名 / revision 规则。不收任何具体 token 字面：Computer-product-specific 错误码（例如 §4 upgrade closed-set 的 attempt-outcome / pre-condition / informational 三族 token，由 Computer product RFC §4.4 (6) inline 持有）按本框架运作但 token 列表留在各自产品 RFC，不在本节登记。引用本节的产品 RFC 自行声明各自 closed-set 的 token 字面 + byte-pin verification 路径。

5.1 注册 (Registration)

稳定错误码必须满足以下条件之一才能被认为已"注册"：

  • 在某个 base / product RFC 中作为 closed-set / 单条 stable code 显式列出。
  • 对应到一个 source-of-truth const file（举例 upgradeLog.ts-style as const 数组、stable enum 模块），且该 const file 路径在 RFC 中被点名作为 byte-pin 来源。

未走以上路径的临时字符串不属于稳定错误码：

  • 仅出现在 stderr / 文案 / Tier-2 用户提示的字符串字面（举例：CLI 一次性 friendlier hint）可以不进 closed-set，但 RFC 必须显式标注其为 Tier-2，并且 product RFC 的 byte-pin gate 不得把它当成 closed-set 成员。
  • 未注册 internal route fail-closed 时回 auth_policy_unregistered_path（见 §2.4）；这是"路由没注册"框架码，不是 wrong-principal 错误。

5.2 命名 (Naming)

  • 稳定错误码使用 UPPER_SNAKE_CASE（举例：NOT_ATTACHED，外部产品 RFC 持有的 Computer-specific 例子）或 lower_snake_case（举例：invalid_principal / cross_agent_act / runner_unavailable / unsupported_capability / capability_not_authorized / auth_policy_unregistered_path，本 base RFC §2 / §4 持有）。两种风格不混用，单个 closed-set 内必须风格一致。
  • 新增 closed-set 时，命名风格 follow 该 closed-set 在 source-of-truth const 中已有的风格；不允许在同一 set 内一半 UPPER 一半 lower。
  • 名字必须描述 failure mode，不能描述实现路径或当前 fix（"避免引用当前 task / fix / callers"原则的延伸）。
  • 错误名一旦注册，禁止 rename：rename 与 delete 同等禁止（见 §5.3）。

5.3 演进 (Revision)

稳定错误码集合的演进遵循三条 meta-rule：

  • Additive-only：新增 failure mode = 在 closed-set 末尾追加，不 复用现有 token 字面、不 重排顺序。
  • 现有 value rename 与 delete 同等禁止：错误名一旦在 RFC 注册过，下一版 RFC 不允许把它改名或移除；rename 等价于 "delete + add"，必须走 deprecation window，并且 deprecation window 内两个名字同时活着、both byte-pinned。
  • 新 failure mode 必须走 RFC bump：新增 closed-set 成员属于 contract 变更，不 走 chore / fix PR；RFC bump（含双签 byte-pin verification）+ source-of-truth const update + 测试 byte-pin 同步必须在同一 PR 或同一 PR 序列内 atomically 落地，避免 const 已加但 RFC 没动 / RFC 已加但 const 没动的 drift 状态。

5.4 Byte-pin / closed-set hardness gate

引用本框架的产品 RFC 在声明自己的 closed-set 时，必须同时落地以下四条 hardness gate sub-rule（"closed-set hardness gate 4-rule family"），缺一不可：

  1. List closed-set must byte-verify source const before publishing。任何"这是 closed-set"的 RFC 表述在 sign-lock 之前必须对照 source-of-truth const file 的 as const 数组逐 token cross-verify；不允许凭记忆写 token 列表。Failure mode 双向：bogus token grep 永远绿（false positive），real token leak 永远不可见（false negative）。
  2. Grep closed-set must use per-token literal, not regex alternation。验证脚本使用 for t in TOKEN1 TOKEN2 ...; do rg -F "$t" "$file"; done 形式。rg -F 'A|B|C' 把 A|B|C 当字面字符串（-F = fixed strings）而非 alternation，会返回 0 hit 即使 A/B/C 实际存在。命中时 emit LEAK: $t 便于 debug。
  3. Verify the verifier。任何 negative grep（"expect 0 hits"）必须先证明它能 catch 已知 leak，再相信"0 hits"输出。Protocol：(a) 注入已知 sentinel token 到 target file → 跑 check → 必须返回非零 + LEAK: $t；(b) 移除 sentinel → 跑 check → 必须返回 0；两个方向都必须成立。否则 self-check 自身可能坏掉而无人察觉。
  4. Verifier cleanup must not break working-tree state。Self-test 不允许使用 git checkout -- $file 类操作做 cleanup（会摧毁 reviewer uncommitted edits）。Pattern 使用 tmp=$(mktemp "${TMPDIR:-/tmp}/<prefix>.XXXXXX"); trap 'rm -f "$tmp"' EXIT; cp $file $tmp; <operate on $tmp>，绝不在原文件上做注入-移除循环。

这四条规则共享 root cause = "literal vs pattern, source vs check" 的层次混淆。任何 closed-set / hardness gate 工作（含 RFC sign-lock 中的 token 列表、byte-pin 测试 fixture、banned-verbatim grep gate、regression guard、contract index sweep、任何"this list is the full set"声明）默认按本节执行。

5.5 Tier 划分

错误信息分两层：

  • Tier-1 (stable code)：API response / structured error 字段的稳定字面（举例 invalid_principal / cross_agent_act / runner_unavailable），closed-set / additive-only / byte-pin verified。
  • Tier-2 (stderr-only friendly hint)：CLI 输出 / human-readable 文案。可以在 patch 版本内调整措辞，不 进 closed-set。但 product RFC 在引入 Tier-2 字符串时仍受"byte-pin literal CLI cross-verify"约束（见 §5.6）。

5.6 Byte-pin literal CLI cross-verify

当稳定错误码的 Tier-2 文案包含 copy-paste-ready CLI command 字面（举例："run some-cli stop to recover"），byte-pin gate 必须 cross-verify 该字面 routes to a working CLI handler，不只 string-match：

  • grep CLI 注册（commander / 等价 framework）确认该 command 已注册，或
  • 在 test sandbox 跑 literal command (--help) 并 assert non-error exit / stderr 不含 "unknown command"。

Sub-pattern：错误信息含 npm i -g @<scope>/<pkg>@<version> 时，必须 verify (a) 包已 publish、(b) version selector 能 resolve（举例 npm view @scope/pkg dist-tags）。

6. Hard non-goals (credential subset)

本节 lifted from Computer RFC v8.3.3 §11 hard non-goals 的 credential / auth-axis subset；语义不变。Computer-product-specific 非目标（举例 upgrade rollback / in-flight turn protection 等）留 Computer product RFC §11，不进 base。

以下事项不在本 base credential RFC 范围内，且不应该被任何产品 RFC 实现成临时捷径：

  1. Computer holding local CA。
  2. Computer locally minting sk_agent_*。
  3. Computer multiplexing agent data plane。
  4. New machine-on-behalf active API surface（legacy /internal/agent/:id/* 仅作 compat，不扩展）。
  5. Workspace fallback to Computer host。
  6. Bare sk_agent_* on legacy /internal/agent/:id/* path。
  7. Runtime CLI / tool shell 直接拿 Slock bearer key（见 §1.4 runner key isolation）。
  8. Send response carrying catch-up unread payload（catch-up 不走 send response）。
  9. 把 credential_last_used_at 当 lifecycle event。
  10. 引入 daemon principal / daemon lifecycle producer。
  11. 让 legacy daemon package 继续承载新产品语义。

实现 PR review 在遇到上述任一条目对应的 "临时捷径" 时应直接拒绝，由 product RFC 走 §5 framework 流程显式决议是否解锁。
