# 评论

人们评论文档，是为了讨论其中的某一段，所以评论应该放在那一段旁边。在文档查看器里，评论放在右侧页边，每张卡片与它所评论的段落对齐，那一段会被高亮。没有空间放页边时，段落旁边的一个标记会在底部面板里打开讨论。在手机上，人们在屏幕底部的一条栏里写评论（[手机上](#on-a-phone)）。Google Docs、飞书文档和 Word 都是这样显示评论的；人们已经熟悉，所以 Raft 不另搞一套。

## 适用范围 {#when-it-applies}

Raft 自己渲染的文档上的评论：文件查看器里的 Markdown、文本或代码文件（[由现有部件组成](../components/overview.md#file-viewer)），以及以后的任何文档界面。不包括对消息的回复，那是消息列（[会话](./conversation.md#threads)）；也不包括 Raft 无法测量内容的文件，比如沙盒 frame 里的页面。Artifact 的 HTML 页面就是这样的 frame，但它的标记画在页面里面，所以有自己的规则：[在 Artifact 上评论](#commenting-on-an-artifact)。

## 结构 {#structure}

```example
comment/compositions/margin
```

- 文档，然后是它右侧的页边：一个由 `CommentCard` 组成的 [CommentMargin](../../packages/ui/src/components/comment/comment.md)，每个 `CommentMarginItem` 放在它那一段的顶部。
- 每张卡片里是评论（[CommentEntry](../../packages/ui/src/components/comment/comment.md#anatomy)），收起时有一行回复数，展开时有回复框（[Composer](../../packages/ui/src/components/composer/composer.md)）。
- 文档里，被评论的段落高亮显示，但不改动文档的 DOM（[高亮](../../packages/ui/src/components/comment/comment.md#highlights)）。

## 规则 {#rules}

- 没有评论的地方什么都不显示：没有空页边、没有占位、没有标记。人们是来读文档的。
- 每张卡片与它那一段的第一行对齐，让视线能从文字直接横移到对它的评论。两张卡片会重叠时，下面那张往下移；卡片从不互相遮挡。
- 每段被评论的文字用浅黄色高亮（`brand` 叠在页面上，浅色模式 35%，深色模式 22%，加 `brand` 下划线）；当前打开的讨论所对应的段落用全黄色加墨色文字：打开的讨论是这个人选中的，而黄色表示你选中的东西（[颜色](../foundations/color.md#meanings-of-color)）。
- 一次只打开一个讨论。它的卡片加上墨色边框并从页边浮起（`shadow-float`），仍然与它的段落对齐，其他卡片给它让开位置。打开的卡片是人们阅读和输入的地方；其他卡片是一份列表，告诉人还有哪里可以读。
- 收起的卡片显示第一条评论（截到 2 行）和回复数。展开后显示所有评论和回复框。页边如果都是完整的讨论，每张卡片都会被推得离它的段落很远。
- 针对整篇文档的评论放在页边顶部，只放一次，并用一行文字说明。不要在每张卡片上重复文件名：查看器已经显示了。
- 找不到对应段落的评论（文档在它下面改了）也放在页边顶部，用一行文字说明（"Position not found"）。永远不要丢掉它，也永远不要把它挂到现在那个位置上的文字上：这条评论仍然是讨论的一部分，挂错了位置，就等于说了一句没人说过的话。
- 在打开的卡片里的 [Composer](../../packages/ui/src/components/composer/composer.md) 回复，用粉色的发送按钮：只有打开的卡片有发送按钮，所以它是这个界面上唯一的粉色按钮。
- 打开一个讨论，它的回复框就直接出现，不管讨论在哪：页边的卡片、浮动卡片，还是所有评论列表里的一行。在这个列表里选中一行，就像页边打开卡片一样打开它，它的段落同时高亮；不需要先按「回复」。没打开的讨论不显示回复框（Kirby，2026-11-26，#proj-workspace:#447）。
- 按 Esc 或打开另一张卡片，关闭当前打开的卡片。

## 发起评论 {#starting-a-comment}

在阅读的地方发起评论；在有人想评论之前，界面上不放评论控件（「没有评论的地方什么都不显示」）。

- 针对一段文字：选中文字后，页边出现一个 Comment 按钮，与选区对齐，和 Google Docs 一样。它在原位打开一张新卡片，回复框获得焦点；选区变成打开状态的高亮，其他卡片给它让开位置，按 Cancel 丢弃这张卡片。第一条评论之前没有页边，所以按钮浮在文档的右边缘，文档只在卡片打开时才让出空间：选中文字永远不会让鼠标指针下的文字移动。
- 新卡片关闭时里面有这个人写的字，就把字留作草稿，并在文档里留下草稿的标记：按 Esc、在页面上点按、用 Tab 离开卡片，以及那段文字消失，都是这样；空卡片直接关闭。Cancel 是例外，它丢掉写的字。草稿在发送之前只属于读者自己，所以不会因为一个人看向别处，他输入的东西就消失。在 Artifact 查看器里，有字的卡片在页面上点按时根本不会关闭（[评论卡片什么时候关闭](#when-a-comment-card-closes)）。
- 针对整篇文档：文档还没有评论时，查看器的 Comments 按钮发起一条评论，放在页边顶部。在手机上，改由底部的对话栏针对整篇文档写评论，不管有没有评论（[手机上](#on-a-phone)）。有了评论之后，这个按钮用来显示和隐藏评论，页边顶部提供 Comment on file，直到出现针对整篇文档的讨论；之后就在那个讨论里回复。按钮的名字要符合它的作用：只有在它是开关时才是开关。
- 页边的头部放它自己的控件，比如卡片的排序，但不放隐藏页边的按钮。查看器的 Comments 按钮负责显示和隐藏页边，两种情况下都在同一个位置，页边显示时它处于按下状态。页边头部里的隐藏按钮读起来像是在原地收起，但它会和页边一起离开，所以回来的路在别处（xxchan，2026-11-22，#proj-workspace:2df75147）。窄布局的底部面板保留自己的关闭按钮，和每个底部面板一样，因为开关就在它下面。
- 锚点暂时还无法定位的选区，变成针对整篇文档的评论，卡片上说明这一点，而不是不显示按钮：人们应该总能对正在读的东西说点什么。
- 在窄布局里，标记列的顶部提供 Comment on file（在手机上由对话栏提供），标记和针对整篇文档的评论在底部面板里打开。用鼠标时，选区上的 Comment 按钮也打开底部面板；在触屏上，选区改为得到键盘上方的回复框（见下）。
- 在触屏上，选区的 Comment 按钮是页面这一列底部的[选中文字的工具栏](../../packages/ui/src/components/text-selection-toolbar/text-selection-toolbar.md#behavior)，从不是在人还在选择时就打开的底部面板：底部面板的遮罩会抢走选区手柄需要的触摸。点按 Comment 也不打开底部面板：一个回复框贴在键盘上方，高一行，前面是关闭按钮，后面是 Send；同一次点按让它获得焦点，所以键盘和键盘的听写马上出现。它能做评论框在别处能做的一切，包括用 @ 提及和附件；文字变长时它会长高几行，然后滚动；一行是它的起始高度，不是截断。它没有标题，也不引用那段文字：那段文字在页面里保持高亮，被抬到回复框上方。页面上可以盖一层浅遮罩；点按遮罩和点关闭按钮一样会关闭回复框，里面的字留作草稿，和新卡片关闭时一样。发送之后，高亮变成这段文字的标记（xxchan、Remy、Kirby，2026-11-25，#proj-workspace:#423）。
- 用键盘时，⌘⌥M（Ctrl+Alt+M，Google Docs 的快捷键）评论选区，这样用 Shift 加方向键选择文字的人永远不用离开文字。Comment 按钮也保留在 Tab 顺序里，排在文档之后，工具提示里显示快捷键。

## 宽屏和窄屏 {#wide-and-narrow}

根据文档能让出的空间，评论有三种形式：文档旁边页边里的卡片；文档旁边的标记，点开是底部面板；页面一点宽度都让不出来时，页面里的标记，点开是浮动卡片。

页边起始宽 340px，可以拖动它的边，在 280px 到让文档剩 360px 之间调整。它记住宽度，并且和所有评论的列表是同一列、同一个宽度：两者占文档旁边同一个位置，来回切换时文档不会移动。有人加宽它，是为了看长回复或代码；停在让文档剩 360px，是因为旁边的文档还要读，这时更窄的文档是这个人自己选的（Kirby，2026-11-26，#proj-workspace:#447）。只在页边最窄时文档还能保留至少 480px（每行约 60 个字符）时显示页边，也就是查看器宽 784px 起（280px 的卡片，加上它和文档之间 24px）；并且只在桌面端显示：用鼠标或触控板、宽度 768px 起，这是所有桌面端尺寸的条件（[间距](../foundations/spacing.md#hit-targets)）。用触屏操作的平板不论多宽都用标记，和手机一样。

测量的是查看器，不是窗口：查看器旁边可能有侧栏或消息列（[响应式布局](./responsive.md#when-a-row-runs-out-of-room)）。卡片和标记是两种不同的结构，不是同一个结构换了样式，所以查看器用 JavaScript 测量自己的宽度，用 [`useCommentMarginFits`](../../packages/ui/src/components/comment/comment.md#wide-and-narrow)，而不是用容器查询。

```example
comment/compositions/viewer
```

- 页边放不下时，把卡片换成每段被评论文字旁边的一个 `CommentMarker`：作者的头像（最多 3 个）和数量。挤到 280px 以下的卡片每一行都会换行，而盖在文档上的卡片会遮住它所评论的文字。
- 点按标记，在底部面板里打开讨论（[Drawer](../../packages/ui/src/components/drawer/drawer.md)）：其中的评论、回复框，以及一个关闭按钮。面板打开期间，段落保持高亮。
- 窄布局里同样保留段落高亮、针对整篇文档的评论（顶部的一个标记），以及位置丢失的评论（在顶部那个标记的面板里，放在一行说明文字下方）。
- 在选区或选中的块上新建的卡片跟随它评论的对象，就像讨论的卡片跟随它那段文字：页面滚动或重新排版时，它一直待在目标旁边，放不下时翻到另一侧，留在文档里面，不盖住应用自己的界面部件。目标滚出视野时，隐藏卡片，但不丢掉写的字，也不丢掉焦点，并在文档的顶边或底边、与目标横向对齐的位置留下一个虚线标记；按这个标记，卡片就在那里重新出现。在触屏上，卡片就是底部面板（如果评论的是选区，就是键盘上方的回复框，见[发起评论](#starting-a-comment)），选中的块保持高亮，页面只抬起刚好够的高度，让目标位于底部面板上方。

```example
comment/compositions/marker-sheet
```

### 一点宽度都让不出来的页面 {#a-page-that-cant-give-up-any-width}

有些文档无法为页边或标记列让位：全宽的 HTML 页面或画布，让位就会在右侧被截掉。这时让页面保持自己的宽度，把标记放进页面里：

- 在每段被评论的文字上显示一个标记，放在页面里，显示它那个讨论里的评论数，和窄布局里 `CommentMarker` 的计数方式一样。不显示这个讨论在页面上的序号："3" 两种意思都能读，而且插入一个讨论会让后面的全部重新编号。
- 点击标记，它的讨论以浮动卡片的形式在标记旁边打开：处于活动状态的 `CommentCard`，包含所有评论和回复框。按 Esc、点它的 ×、在里面没有输入内容时点击它外面，或把标记滚出视野，都会关闭它；里面有字的卡片在点击外面时保持打开（[评论卡片什么时候关闭](#when-a-comment-card-closes)）。页面滚动时它随标记移动。Figma 就是这样显示评论图钉的。卡片宽 320px，不能调宽：它盖在页面上，越宽挡住的内容越多。讨论长时在卡片里滚动，卡片最高是视口高度减去上下各 16px（Kirby，2026-11-26，#proj-workspace:#447）。
- 在触屏上，标记打开底部面板，和窄布局一样。
- 保留高亮。产品如果有一份所有评论的列表，在这种布局里它就是唯一的列表；在页边布局里，页边本身就是列表，所以不要同时打开两者。

## 手机上 {#on-a-phone}

在手机上，人们全屏读文档，只有一只拇指空着，所以写评论只有一个地方：查看器底部的一条对话栏，始终都在，用来针对整篇文档写评论。文档允许选择时，选中一段文字就是评论这一段。要先找一找才能找到的栏，比如挤满东西的头部里的一个图标，或者列表末尾一个盖住页面的输入框，都被人错过了：人们把链接复制到浏览器里，去谈论他们正在读的东西（artin 和 DiRenJie 从一位用户那里听到的，2026-11-25，#proj-mobile:#366）。设计是 Kirby 做的，经过 Remy 和 Lagoon 审阅，由 xxchan 批准（2026-11-25，#proj-mobile:#366）。

这适用于手机的布局。平板、分屏和应用的桌面模式按桌面端的样子布置查看器，没有对话栏。用触屏操作的平板仍然不论多宽都用标记，从不用页边（[宽屏和窄屏](#wide-and-narrow)）；它在触屏上用的东西（选区的工具栏、键盘上方的回复框）遵循[发起评论](#starting-a-comment)。

### 对话栏 {#the-talk-bar}

- 栏里放两样东西：开头是评论数，即评论图标加数量，作为一个打开评论列表的按钮；然后是一个看起来像输入框的控件，占满这一行的其余部分。别的都不放：不放麦克风，因为键盘弹出后，键盘自己的听写只要点一下；也没有要进入的评论模式。0 条评论时，计数只显示图标，不带数字：「0」读起来像是要去查看的东西。
- 输入框高 44px，用控件的圆角 `control-radius`（触屏上 10px），和手机上其他所有输入框一样，从不做成胶囊形：全圆角只用于开关、单选按钮和拖动条（[形状](../foundations/shape.md)）（xxchan，2026-11-25，#proj-mobile:388d92ed）。
- 它的占位文字说明谁会听到：文档是 Agent 写的时，写作者 Agent 的名字，否则写文档本身。具体文字由产品的页面给出。
- 栏上不用粉色。发送按钮是粉色的，只在有文字要发时才出现。
- 把这条栏做成一个画成输入框样子的按钮，而不是真正的输入框。按下它会打开键盘上方的回复框，也就是选区的 Comment 打开的那个（[发起评论](#starting-a-comment)），带提及和附件，并让它获得焦点，这样键盘马上出现。留在屏幕底部的真正输入框，在获得焦点的那一刻会让 iOS 滚动页面。
- 让这条栏避开系统的主屏幕指示条：底部安全区在栏的下面，不在栏里面。
- 回复框关闭时里面有字，就把字留作草稿，和新卡片一样。手机上没有「先存草稿」（Save draft）按钮，也没有草稿的底部条：有草稿时，状态行会说明，并带 Send（"2 unsent drafts · Send"，[发送之后](#after-sending)）；草稿在评论列表里修改或删除，那里有 Undo。

### 一次一条栏 {#one-bar-at-a-time}

- 底部一次只显示一样东西：对话栏；有选区时，是[选中文字的工具栏](../../packages/ui/src/components/text-selection-toolbar/text-selection-toolbar.md#behavior)；或者是键盘上方的回复框。每一样都取代前一样，选区或回复框消失后，对话栏回来。叠在一起的话，选区工具栏、输入框和键盘会让页面没有地方可读。
- 选区工具栏只放 Comment 和 ×，× 清除选区。不要放 Copy：选区旁边系统自己的菜单里总有它，下面再放一个 Copy 就是同一个操作出现两次（Lagoon，2026-11-25，#proj-mobile:388d92ed）。
- 不接受选择的文档（产品可以为自己的某个页面这样决定）只从对话栏得到评论。

### 评论列表 {#the-list-of-comments}

- 从栏上的计数，或从一个直接指向列表的链接，打开列表，作为底部面板，底部是同一条对话栏，从不另设一个自己的输入框：整篇文档只有一个写的地方。
- 列表打开时什么都不要获得焦点。只有在人按下对话栏或某个讨论的 Reply 时，键盘才出现：打开来读的列表，被键盘盖住一半，就没法读了（Lagoon，2026-11-25，#proj-mobile:388d92ed）。

### 发送之后 {#after-sending}

- 有关于这个人的评论的事要说时，在对话栏正上方显示一行状态。把它画成实心的一行，不是浮着的一行字：高 36px，和对话栏一样宽，在 `layer-card` 上，上面一条 `line-seam`，下面是对话栏自己的顶线；先是作者的头像，然后是加粗的作者名和那句话，末尾是 ›。它下面是文档，文档可以是任何颜色，所以没有自己背景的一行字，盖在上面就读不清。
- 作者在工作时，头像带着表示正在工作的灯，静止不动，和[正在工作的 Agent](../people-and-agents/working-agents.md#motion) 一样：没有跳动的圆点。
- 一次只显示一句话，取下面第一条成立的：
  1. 草稿加载失败或发送失败：说明这一点，带 Retry。
  2. 作者在怎样处理发过去的东西：
     - "Bugen is working on it · Got your comment"，作者是一个正在处理这份文档的评论的 Agent 时。只在有信号表明它在处理时才这样说，从不根据输入来猜：Agent 大部分时间在阅读和编辑，而不是在输入消息（Remy，2026-11-25，#proj-mobile:388d92ed）；
     - "Bugen replied"，作者用一条回复作答、没有修改时：这是对一个问题通常的回答；
     - 以及产品为文档的修改加上的内容，比如一个新版本。
  3. 未发送的草稿："2 unsent drafts · Send"。
  4. "Sent to Bugen"，在没有信号表明作者在工作时。它排在未发送的草稿之后，因为它可能一直持续到文档关闭：如果排在草稿前面，一个人发了一条评论、又把另一条留作草稿，就永远看不到 "2 unsent drafts · Send"（Jasper，2026-11-25，#proj-mobile:#366）。
- 只有当这一行在说作者在做什么、或者说一条评论已经发出时，整行才是一个按钮：它在相关的地方打开评论列表，也就是刚发出的评论、作者的回复或那次修改。对草稿和 Retry，只有那个操作（Send、Retry）是按钮：按钮里面的按钮没法分开按。
- 这一行说的事结束了，就让它消失。"Sent to Bugen" 在相应的事发生时变成「working」「replied」或产品的修改，否则一直留到文档关闭。回复和产品的修改，在这一行被按下或文档关闭时消失。草稿和它们的失败，在没有剩下要发送或重试的草稿时消失。
- 状态行下面的对话栏保持可用：作者工作时，这个人可以继续说。
- 有选区时，把这一行连同它所在的对话栏一起收起。

## 在 Artifact 上评论 {#commenting-on-an-artifact}

Artifact 查看器显示两种页面：占满查看器的 HTML 页面，和 Raft 自己渲染的 Markdown 文档。在这两种页面上，人们可以把一条评论马上发出，也可以先存成草稿、再把草稿一起发送，而且开始之前不用在两者之间选。这些规则是 xxchan 定的，来自定稿的设计稿（Artifact「Raft 评论体验」的 v8，YL2pf8ML79U9jovzB5PhBF；2026-11-04，#proj-workspace:1c7b5037）。和[发起评论](#starting-a-comment)不一致的地方，在 Artifact 查看器里以这里为准。这些规则用于桌面端布局。在触屏上，不论多宽，HTML 页面都不接受选区，也不接受选中的元素，所以没有评论模式，也没有「选元素」（Pick elements）（[Artifact 页面](../products/raft-chat/artifact.md#on-a-touch-screen)）。在手机上，查看器也没有评论的分体按钮、没有草稿的底部条，也没有「先存草稿」（Save draft），并遵循[手机上](#on-a-phone)。

- 选中文字，马上出现「评论」（Comment），不用先进入评论模式。它是一个只有文字那么宽的按钮，紧跟在选区末尾。评论是马上发出还是先留着，在评论框里选，不在这里选。
- 评论框里放两个按钮：「发送」（Send），发出评论并通知它涉及的人；「先存草稿」（Save draft），把评论留在页面上，只有作者自己看得到。有了草稿之后，Enter 按的是「先存草稿」，⌘Enter 按「发送」，免得攒了一半误发出去。
- 评论框下面什么都不写。「发送」会通知谁（"Notifies Judith (author)"）放在「发送」的工具提示里，输入框的占位文字已经提示可以 @ 某人；每个框下面都有一行字，每写一条评论都要读一遍，说的又是按钮已经说了的事。
- 查看器头部的评论按钮保持原来的分体按钮：主体部分进入和退出评论模式，▾ 打开所有评论的列表，带评论数。它不显示草稿数：底部条已经数着草稿，同一件事数两遍，读起来像两件要做的事。对整个 Artifact 的评论，照旧写在这个列表最下面的输入框里。
- 底部条放在查看器底部，只有这几样，按这个顺序：「选元素」（Pick elements，只在 HTML 页面上）、撤销和重做、「放弃」（Discard），以及「发送 N 条」（Send N）。「发送」只带上数字，不写「草稿 2 条 · 一起发送」：数字是这个标签唯一需要多说的。
- 只在有草稿、或者这个人在评论模式里时显示底部条，其他时候隐藏，这样它不会挡住没人在评论的页面。
- 在 HTML 页面上进入评论模式时，「选元素」默认打开：悬停时框出一个元素并标出它的类型（`h1`、`p`），点一下就在它旁边打开评论框，用来评论图片、按钮、卡片这类没有文字可选的地方。关掉它就回到正常浏览，选中文字照样能评论。Markdown 文档没有元素可选，所以那里的底部条没有「选元素」。
- 「发送 N 条」点了就直接把草稿全部发出，不弹清单，也不再确认（xxchan，2026-11-04：「点发送 2 条没必要再确认了」）。要改或删某条草稿，在页面上点开它。「放弃」在原地确认之后才丢掉草稿。撤销和重做（⌘Z 和 ⇧⌘Z）逐步撤回或重做对草稿的改动。
- 在 HTML 页面上，已发的讨论显示为段落末尾的一个标记，带作者的头像和条数，画在页面里（[一点宽度都让不出来的页面](#a-page-that-cant-give-up-any-width)）；草稿显示为一个虚线小图钉，点开才看到内容。页面占满查看器，所以旁边不放任何 Raft 自己的东西：没有卡片栏，也不在元素旁边挂一张写着草稿内容的卡片。
- 在 Markdown 文档里，讨论和草稿都放在右侧的页边栏里，每张卡片与它的段落对齐（[规则](#rules)），草稿的卡片注明它是只有作者看得到的草稿。页边放不下时，换成标记（[宽屏和窄屏](#wide-and-narrow)）。
- 文本文件和 CSV 文件不属于这两种页面：它由 Raft 绘制，它的评论总是显示为它旁边的标记，从不显示为卡片。在这里，草稿显示为一个单独的 `CommentMarker`，与它所评论的那些行的第一行对齐：虚线、空心，没有头像也没有条数，和 HTML 页面上草稿的图钉一样，这样不管在哪种文件上，草稿都显示在它被写下的地方。点按它，在它旁边打开草稿，在手机上则在底部面板里打开；所有评论的列表开着时，点按它改为跳到列表里这条草稿的卡片。它评论的那些行不高亮。回复草稿没有标记：它显示在它所在讨论的回复下面。
- 从所有评论的列表里、或从讨论的回复下面删除草稿，不用确认：只有作者看得到它，而且轻提示（"Draft deleted"）带撤销，和任何从列表里拿走的东西一样（[确认](./feedback.md#confirming)）。撤销只把这一条草稿恢复到原处，不管之后改了什么；轻提示消失后，⌘Z 仍然能把它恢复，底部条显示期间，底部条上的撤销也能，直到查看器关闭，或者「发送 N 条」或「放弃」清空了历史。有三种删除要先确认：带图片的草稿，图片的上传会随它一起删掉，所以没法恢复；草稿自己的视图（点它的标记、图钉或卡片打开的那个）里的「删除」（Delete），因为同一个视图也能从 HTML 页面的图钉打开，而页面自己就能触发图钉，这个视图不管从哪里打开，删除的方式都一样；以及已发的评论，它会对所有人删除。

### 评论卡片什么时候关闭 {#when-a-comment-card-closes}

Artifact 查看器里的每张评论卡片都按同一条规则关闭，由它里面有没有字决定，而不是由它是哪种卡片决定：讨论的卡片、页边栏里的卡片、新评论的卡片、针对整个页面的评论框，以及讨论回复下面的回复框，在 HTML 页面上、在 Markdown 文档里和在附件的预览上都一样（Kirby，2026-11-23，#proj-workspace:#385）。

- 空卡片在它外面任何地方被点按时关闭，包括在页面上点按。HTML 页面是一个单独的 frame，但对人来说它是同一个屏幕，而空卡片没有什么可丢的。
- 有字的卡片在它外面被点按时保持打开。它只在按 Esc 或点它的 × 时关闭，按 Esc 会把字留作草稿：在页面上点按往往只是再看一眼那段文字，字永远不会因此丢掉。
- 点按卡片已经打开的标记或图钉，会关闭那张卡片，不会再打开它一次。
- 在查找栏外面点按（包括在页面上）时，查找栏保持打开，因为人们会在那里点按来看它找到了什么。按 Esc 关闭它，焦点在页面里时也一样。
